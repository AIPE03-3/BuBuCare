## Q7 — 前端請求如何從後端到 agent 【擋 P3.2 與 P5.3】

> 2026-07-20：草稿改為即時產生後，`POST /agent/draft` 與 `POST /agent/ask` 是同一個架構問題，
> 因此本題同時擋住 P3 與 P5。拍板一次，兩期都解鎖。

**已確定的部分**：請求路徑是 `前端 → 後端 → agent`，不是前端直連 agent。依據（皆為程式碼事實）：

1. agent 目前是 Kafka consumer 迴圈（`agent/main.py` 的 `run()`），沒有 HTTP 介面、沒有驗證、沒有 CORS。
2. JWT 驗證需要 `SECRET_KEY`（`backend/core/auth.py`）。agent 自己驗 token 等於把簽章密鑰複製到第二個服務，多一個外洩點。
3. `company_id` 過濾需要 DB。後端有 session，agent 沒有。詳見下方發現。

**未拍板的部分**：後端收到請求後，怎麼觸發 agent 的 QA 圖？

| 方案 | 部署 | 慢請求影響 | 改動成本 |
|---|---|---|---|
| (A) 同進程 import（backend 直接 import `agent.qa`） | 不變 | 佔住 backend worker（LLM 實測 4–10 秒） | 低 |
| (B) 獨立 agent HTTP 服務（backend 轉發） | 多一個服務 | 隔離，可獨立擴縮 | 高 |

建議：**MVP 走 (A)**，LLM 呼叫丟 threadpool 避免卡住 event loop。問答不在 MVP 路徑（P5 排在 P2 之後），為它先拆服務是過度設計；真遇到延遲或擴縮問題再換 (B)，改動只在後端一個函式，agent 的 QA 圖零改動。

### 連帶發現一：company_id 不在 JWT 裡 【擋 P5.1 的強制過濾要求】

03 檔 §4 要求「一律強制 `company_id` 過濾」，但登入時放進 token 的只有：

```python
create_access_token(data={"sub": user.name, "role": user.role})   # backend/users/router.py:75
```

`company_id` 在 `user_account` 表上（`backend/core/models.py:32`），**光靠 token 解不出來**。因此問答入口一定要多查一次 user 表拿 company_id，或改動登入流程把 company_id 放進 token（後者影響既有 token，需評估相容性）。實作 P5.3 前要先決定用哪個。

### 連帶發現二：「物理上無法寫入」需要唯讀 DB 帳號

P5.1 驗收標準寫「工具層物理上無法執行寫入」。若 QA 工具共用 backend 現有的 `get_db` session，這個保證不成立——那條 session 是可寫的。要真正達成，需另開一個**使用唯讀 DB 帳號**的 engine 給 QA 工具。此事與 (A)/(B) 無關，兩種方案都要做。

## Q8 — 視覺模型 【✅ 已落地，但驗出新問題】

**已完成 2026-07-20**：開發機安裝 `qwen2.5vl:7b`（6.0 GB），真實監視器畫面端到端跑通。

| 項目 | 結果 |
|---|---|
| 管線 | ✅ 圖檔 → VLM → judge → 策展 → Kafka 訊息，全程通 |
| 每筆耗時 | 約 **30 秒**（VLM 18.6s + judge 7.7s，含模型切換） |
| 真跌倒 4 張 | ✅ 全部判為 `true_alarm`，零漏報 |

**模型分工（實測後拍板）**：`AGENT_VLM_MODEL=qwen2.5vl:7b` + `AGENT_LLM=ollama:qwen2.5:7b`，
兩個模型都要留。曾評估只用 `qwen2.5vl` 一個以省下每筆約 8 秒的模型切換，但實測否決：

| 模糊情境（應說「我不知道」） | `qwen2.5:7b` | `qwen2.5vl:7b` |
|---|---|---|
| 全黑／嚴重遮蔽／過曝 等 5 例 | 危險判定 **0/5** | 危險判定 **3/5** |

`qwen2.5vl` 在完全看不到畫面時會用 0.80 的信心判 `false_alarm`。**視覺模型不可兼任推理腦。**

### 遺留問題一：篩選能力接近零 【擋 P2.4】

5 張真實畫面**沒有任何一張**被判成 `false_alarm`（含一張站立行走的畫面）。
Agent 存在的目的是幫值班人員濾掉誤報，目前它每一筆都往上報——安全，但沒有減輕負擔。

已修掉一部分成因（VLM 誘導性 prompt、judge 數字比較錯誤，見 01 檔 §4 附近註解），
但 judge 的安全偏向仍強，證據明確時也不肯說 `false_alarm`。
需要更多標註樣本才能校準，屬 shadow 階段工作。樣本數 5 張，結論信心度有限。

### 遺留問題二：模型對 prompt 高度敏感

同一張夜視畫面：五題結構化提問答「正在行走」（正確），簡短自由提問答「躺在地板上」（錯誤）。
中性 prompt 有效，但穩健性有限，換 prompt 前後都要重測。

### 遺留問題三：吞吐

每筆 30 秒。Q3 放寬門檻（0.55 → 0.35）後告警量會上升，需回頭評估是否跟得上（01 檔 §7）。

## Q10 — 時序資訊：Agent 拿不到，但那才是判斷跌倒的關鍵 【擋篩選能力改善】

**問題**：單張靜態畫面分不出「躺著休息」與「跌倒」。邊緣端的 Action Transformer 吃 30 frame
窗口正是為此，但 Agent 只拿到一張快照，時序資訊在傳遞過程中被丟掉了。

**已排除的兩條路**（2026-07-20 實測）：

1. **VLM 直接看影片** —— 不行。ollama 的訊息型別只有 `images`，沒有影片欄位
   （Qwen2.5-VL 模型本身支援影片，但要走 transformers / vLLM 等其他服務堆疊）。
2. **一次送多張圖** —— 不行。ollama 上的 `qwen2.5vl` 多圖不可靠：同樣兩張圖只調換順序，
   描述就從全錯變成全對，沒有穩定把圖對應到編號。客戶端已支援多圖（有測試），但這個模型用不了。

**也不能從 `clip_path` 抽幀**：那是**整支來源影片**的路徑（`test_demo/test1.mp4`），
不是事件片段，訊息裡也沒有幀索引或影片內時間偏移，定位不到跌倒發生的那幾秒。

**尚未評估的路**：

- **把連續幀拼成一張圖**（filmstrip / 2×2 網格，標上編號）。模型只需看懂一張圖，
  多圖對應的問題不存在，時序資訊保留。需要 `pillow`（約 3 MB）。
- 前提仍是**邊緣端要送連續幀**：他們手上本來就有 `frame_window`，觸發時把那幾幀
  跟 snapshot 一起存下、多送一個檔名清單即可。改動小，但屬跨人協調（同 P2.0）。

## Q9 — al_curator 的 priority 校準偏鬆 【不擋功能，擋實用性】

> **本題作廢（2026-08-10）**：`al_curator` 已移除，見
> [`docs/CHANGELOG-STAGES.md`](../../docs/CHANGELOG-STAGES.md) 第 15 項。
> 以下實測結果保留 —— 日後若再做 LLM 挑樣本，「priority 全給 high」是已知的第一個坑。

**現況**：以 `qwen2.5:7b` 實測三個情境，`priority` **全部給 `high`**：

| 情境 | yolo | keep | priority |
|---|---|---|---|
| 低分卻是真跌倒（漏抓盲點） | 0.41 | 收 | high |
| 高分卻是誤報（誤觸發盲點） | 0.92 | 收 | high |
| 判得又快又準（無學習價值） | 0.55 | 收 | high |

`keep` 的判斷是對的——第二例正是舊寫死規則（0.35–0.85）漏掉的樣本，證明換掉規則有效。
但 **`priority` 全 high 等於這個欄位沒有鑑別力**，日後 `grep '"priority": "high"'` 會撈出全部樣本，
挑樣本的功能形同虛設。第三例也顯示 curator 傾向多收。

**為什麼不現在調**：沒有真實樣本就調 prompt，只是換一種猜法。過度收錄的代價只是硬碟空間與
資料集稍雜，不影響告警安全。

待辦：shadow 階段累積真實樣本後校準，可能的方向是給 priority 加上明確的分配比例約束，
或改用規則後處理（例如依 |yolo_score − verdict| 的落差自動分級）。

### 補充：裝置歸屬錯誤比原本記錄的嚴重（2026-07-20 核對程式碼發現）

原本這張表寫的是「camera_id **非數字時** fallback 寫死 101」，語氣像是偶發狀況。實際上：

```python
cam_id = event_data.get("camera_id", "Unknown_Room")               # vlm_worker.py:67
clean_device_id = int(cam_id) if str(cam_id).isdigit() else 101    # vlm_worker.py:149
```

- 跌倒告警**根本沒有 `camera_id` 欄位** → 拿到預設值 `"Unknown_Room"` → 不是數字 → **101**
- 巡檢的 `camera_id` 是 `"Room_301_Bed"` → 也不是數字 → **101**

**所以線上每一筆慢車道事件都被記到裝置 101**，不論實際是哪台相機。而正確的 `device_id`
一直都在訊息裡（邊緣端算好的），只是沒人讀它。

這件事在 Agent 的測試裡看不出來，因為測試資料是照文件範例造的——而文件範例是錯的。
教訓：**契約要以程式碼為準，不要以文件為準**。已於 03 檔 §1 改為直接抄錄程式碼。
