## 2. PRD 產品需求文件

### 2.1 產品願景與定位

Fulilian 是一套為安養機構設計的 **human-in-the-loop agentic 照護編排系統**。它以公共區域監視器影像作為感知輸入，於本地端進行情境推理，再由 Agent 編排層協調「複判 → 分流 → 派工 → 升級 → 復盤」的完整事件生命週期；所有關鍵動作（通報、升級、送醫建議）皆保留人工確認，並以內建的 **MLOps 資料飛輪**讓系統在運作中持續降低誤報、自我改善。核心目標是把照護工作從被動應變，轉化為**可偵測、可分流、可追蹤、可預防、且可持續改善**的結構化流程。

**系統的差異化不在感知模型本身**（VLM 已商品化），而在於三項工程支柱：

#### 支柱一：Agentic 事件編排

系統不只「偵測到事件」，而是由 Agent 依事件狀態自主協調工具調用——查值班表、定向派工、逾時自動升級、草擬交班紀錄——把單點偵測升級為閉環的事件處理流程。

#### 支柱二：Human-in-the-loop 與抗警報疲乏的中控台設計

Alarm fatigue（警報疲乏）本質上是產品與互動設計問題，而非模型問題。系統以兩段式複判 + 信心分數 + 事件分級，讓值班人員只在「真的需要」時被打擾；中控台的事件呈現、一鍵接手／結案／標記誤報的互動流程，皆以降低照護人員認知負荷為設計目標。送醫、對外通報家屬等關鍵動作一律由人工確認，系統僅提案與草擬。

#### 支柱三：MLOps 資料飛輪與模型治理

每一次「誤報標記」都成為改善燃料：誤報影像進入 Hard Negative Pool，累積後用於 fine-tune；新模型須通過固定測試集的部署門檻（Recall 不退步、誤報率惡化不超過 10%）才允許由人工審核升格 Production，並保留一鍵回滾。系統因此具備可量測、可驗證、可演進的工程閉環，而非一次性的 demo。

**感知輸入（兩個來源）：**

- **跌倒事件感知**：YOLO 高召回初篩 → VLM 情境複判，對曖昧情境（坐地、伸展、彎腰、攙扶）正確抑制誤報，確認後進入事件生命週期。
- **環境安全度評分**：定時截圖，由 VLM 依五個固定向度評分（總分 100），評分大幅下降時主動提醒值班人員並提示長者避開——把預防提前到跌倒發生之前。

#### 為什麼這題在 2026 仍有價值

- **題目落在當前最受重視的工程能力交集**：agentic 編排、eval／部署門檻、MLOps 監控、human-in-the-loop 工作流程設計——這些正是 2026 AI 應用工程職缺從「會 prompt」轉向「能交付可靠系統」後最看重的能力
- **領域需求真實且具地域性**：台灣已進入超高齡社會，照護人力壓力持續上升，跌倒處置具高度時間敏感性
- **差異化來自系統工程而非模型**：市面感知模型已商品化，真正的護城河在場域流程整合、隱私優先的地端架構、誤報治理飛輪與環境預防——這也正是本系統的設計重心

### 2.2 問題陳述（痛點）

| 利害關係人 | 目前的痛點 |
|-----------|-----------|
| 高齡者（照護對象） | 跌倒後未被即時發現恐錯過黃金處置時間；穿戴式裝置不一定願意長期配戴 |
| 照護員 / 機構 | 人力吃緊、巡視頻率高；一般監視器只能事後調閱，無法即時辨識並通知；環境危險因子無主動提示 |
| 既有 AI 方案 | 單張影像分類易誤報，造成警報疲乏；缺乏事件分流、復盤與隱私治理；無環境安全預警機制 |

### 2.6 關鍵使用者情境

#### 情境 A：曖昧情境的正確抑制（核心展示點）

長者坐在地板上做伸展運動。傳統姿態分類器因偵測到「人在地面」而誤判為跌倒。Fulilian 的 VLM 複判層理解情境後判定為「自主地板運動、無痛苦徵兆、持續有動作」，**抑制此警報**，影像存入 Hard Negative Pool 以供未來訓練。

#### 情境 B：真實跌倒的自動分流與升級

偵測到真實跌倒後，VLM 確認事件、評估嚴重度並草擬通報訊息；Agent 定向通知該區值班照護員；若設定時間內無人標記接手，**系統自動升級**（加派人員、通知組長）；照護員到場處理後標記結案，系統自動產生交班／事故紀錄。

#### 情境 C：環境安全異常偵測

定時評分中，走廊攝影機偵測到拖把桶未收回且地面有積水，本次評分從 82 分降至 55 分，超過異常閾值。系統立即通知值班人員前往處理，並在中控台標示該區為「暫時危險區域」，提示長者避開。

### 2.8 產品風險與緩解

| 風險 | 影響 | 緩解 |
|------|------|------|
| VLM 推論延遲／資源消耗 | 影響即時性 | 跌倒複判僅在規則初篩疑似時觸發；環境評分為非即時週期任務，不佔用即時推論資源 |
| 自演資料集規模有限 | 泛化不足 | 誠實列為後續工作；聚焦於可展示之曖昧情境集；Hard Negative Pool 為未來 fine-tune 準備 |

| 冷卻機制造成漏報 | 同一人二次跌倒被抑制 | 冷卻時間設計保守（預設 5 分鐘）；空間層備援保護 |

## 3. SRS 軟體需求規格書

### 3.1 整體描述

- **產品觀點**：多模組軟體系統，輸入為公共區域影像串流，輸出為結構化照護事件、即時通報、環境安全評分與中控台呈現；採兩段式判斷（規則初篩 + VLM 複判）與事件導向流程，並由 AI Agent 協調工具調用
- **使用者類別**：值班照護員（staff）、機構管理者（admin）
- **一般限制**：本地端推論、edge-ready、Docker Compose 部署；僅處理公共區域影像

### 3.2 功能需求（FR）

#### FR-1 感知與初篩

| 編號 | 需求 |
|------|------|
| FR-1.1 | 系統應能接入 RTSP（機構公共區域監視器）影像串流並逐幀讀取 |
| FR-1.2 | 系統應對畫面進行人體姿態估測，取得關鍵辨識點 |
| FR-1.3 | 系統應對人物進行多目標追蹤，以辨識同一人由站立轉為倒地之過程 |
| FR-1.4 | 系統應依規則（重心高度變化、身體傾斜角度、下墜速度、倒地持續時間）以高召回率篩出「疑似跌倒」事件 |
| FR-1.5 | 系統應實作冷卻機制：同一追蹤目標（Track ID）觸發事件後，在設定冷卻期間（預設 5 分鐘）內不重複建立事件；若 Track ID 因目標消失而重新分配，以倒地位置空間鄰近度（bounding box 中心點距離閾值內）作為第二層保護 |

#### FR-2 VLM 情境推理（跌倒複判）

| 編號 | 需求 |
|------|------|
| FR-2.1 | 當初篩判定為「疑似」時，系統應將事件影像片段送入 VLM 進行複判 |
| FR-2.2 | VLM 應輸出結構化結果，至少包含：是否為跌倒、信心分數、嚴重度、情境描述、建議處置、通報訊息草稿 |
| FR-2.3 | 系統應能依 VLM 結果將事件分級為「疑似／確認／誤報」 |
| FR-2.4 | VLM 應對曖昧情境（坐地、伸展、彎腰、攙扶）正確抑制無效警報 |

#### FR-3 Agent 編排

| 編號 | 需求 |
|------|------|
| FR-3.1 | 系統應依事件所屬區域查詢值班表，定向通知對應照護員（非全員廣播） |
| FR-3.2 | 系統應追蹤事件是否於設定時間內被標記「接手」 |
| FR-3.3 | 若逾時未被接手，系統應自動升級通報（加派人員並通知管理者） |
| FR-3.4 | 系統應能依事件資料自動草擬交班／事故紀錄供人工審核 |
| FR-3.5 | 送醫、對外通報家屬等關鍵動作不得自動執行，須由人工確認 |
| FR-3.6 | Agent 應能判斷何時觸發跌倒複判工具、何時觸發環境安全評分工具，並根據事件狀態決定後續處置流程 |

#### FR-4 事件中樞

| 編號 | 需求 |
|------|------|
| FR-4.1 | 系統應接收邊緣端送來之事件（JSON 警報 + 影片片段）並建立事件紀錄 |
| FR-4.2 | 系統應維護事件生命週期狀態：建立 → 通報 → 接手 → 結案，及誤報抑制、冷卻抑制與升級分支 |
| FR-4.3 | 系統應保存事件影像片段（事發前後數秒）並產生可存取連結 |

#### FR-5 中控台與通報

| 編號 | 需求 |
|------|------|
| FR-5.1 | 中控台應即時顯示事件清單、影像截圖、信心分數與處理狀態 |
| FR-5.2 | 系統應以 Web Push 即時推播通報（LINE Bot 列為後續工作） |

| 編號 | 需求 |

## 4. SAD 軟體架構文件

### 4.1 核心設計原則

1. **兩段式串接（Cascade）**：便宜的規則初篩高召回篩疑似；昂貴的 VLM 僅在疑似時觸發，兼顧召回與誤報抑制
2. **時間序列而非單張判斷**：跌倒為「站立→失衡→快速下墜→橫躺→持續不動」之歷程，需多目標追蹤
3. **Human-in-the-loop**：Agent 僅提案、草擬、分流；關鍵動作保留人工確認
4. **隱私優先、Edge-ready**：本地端推論、影像不出場；架構可部署至邊緣
5. **VLM 一模型雙任務**：同一 VLM 服務同時承擔跌倒複判（即時觸發）與環境安全評分（週期觸發），透過不同 system prompt 區分任務
6. **併發優先序**：跌倒複判為即時安全任務，優先序高於環境評分；若兩任務同時請求 VLM，環境評分請求進入佇列等待，待跌倒複判完成後再處理，避免搶占即時推論資源（詳見 5.5 Agent 編排設計）

### 4.2 五層架構

| 層 | 職責 | 歸屬 |
|----|------|------|
| 感知與初篩 | 影片串流 → 姿態 → 追蹤 → 規則高召回篩 + 冷卻過濾，輸出「疑似事件」 | 既有骨架 |
| VLM 情境推理 | 複判曖昧情境（跌倒）、定期評估環境安全度、輸出結構化結果 | **新增智能核心（主秀）** |
| Agent 編排核心 | 協調工具調用（跌倒複判 vs 環境評分）、派工、逾時升級、文書自動化 | 新增智能核心 |
| 事件中樞與資料 | FastAPI + PostgreSQL + 影像片段儲存，維護事件與環境評分生命週期 | 既有骨架（強化） |
| 應用與通報 | 中控台、環境安全面板、Web Push／LINE | 既有骨架 + 新增 |

### 4.5 關鍵架構決策（ADR）

| 決策 | 選擇 | 理由 / 取捨 |
|------|------|-------------|
| 跌倒判斷方法 | 規則式時序判斷，不訓練深度時序模型 | 時程有限；規則邏輯已可成立，降低訓練資料與時間成本 |
| 誤報治理 | VLM 兩段式複判 + 事件分級 + 信心分數 + Hard Negative 回饋 | 直接緩解 alarm fatigue，Hard Negative Pool 為未來 fine-tune 準備 |
| 環境安全評分方法 | VLM 固定向度評分而非自由評估 | 固定向度讓分數具可比性、可趨勢化；自由評估難以計算分數差異 |
| VLM 任務切換 | 同一 VLM 服務，以不同 system prompt 區分任務 | 減少資源消耗；跌倒複判為即時任務，環境評分為週期任務，不衝突 |
| 長者歸戶（風險預測） | 床位／區域綁定（非生物識別） | 兼顧隱私；避免人臉辨識的法務風險 |
| 資料庫 | PostgreSQL | 正式系統觀感與關聯完整性 |
| 事件傳遞機制 | Kafka | 取代輕量訊息代理，承擔推論事件、狀態變化與 MLOps 回饋資料的高吞吐傳遞，為後續多攝影機／多模型擴展預留擴充性 |
| 訓練管理與模型治理分工 | ClearML（訓練任務、資料版本、實驗追蹤）+ MLflow（Model Registry、Staging/Production/Rollback） | 訓練流程與模型上線治理分離：ClearML 負責訓練端的任務排程與資料版本控管，MLflow 專注模型生命週期治理，避免單一工具承擔過多職責 |
| 部署 | 本地 / edge-ready，Docker Compose | 場域更適合地端；MVP 無需 K8s |
| 自動化邊界 | Human-in-the-loop | 醫療與法務責任，關鍵動作保留人工 |

### 5.2 VLM 推理層設計

VLM 服務承擔兩個任務，透過不同 system prompt 切換，輸出格式各自獨立。

---

#### 任務 A：跌倒情境複判

**輸入**：事件影像片段（事發前後數秒）+ 初篩附帶之骨架／追蹤摘要

**結構化輸出（JSON）**：

```json
{
  "is_fall": true,
  "confidence": 0.92,
  "severity": "medium",
  "scene_description": "長者向右側倒地，雙腳無法自行支撐...",
  "recommended_action": "立即前往確認傷勢",
  "draft_notification": "B 區 14:32 偵測到疑似跌倒事件，請前往查看。",
  "ambiguity_flag": false
}
```

| 欄位 | 型別 | 說明 |
|------|------|------|
| `is_fall` | boolean | 是否判定為跌倒 |
| `confidence` | float (0–1) | 判定信心分數 |
| `severity` | enum | `low` / `medium` / `high` |
| `scene_description` | string | 情境的自然語言描述（繁中） |
| `recommended_action` | string | 建議處置 |
| `draft_notification` | string | 草擬之通報訊息 |
| `ambiguity_flag` | boolean | 是否為易誤判的曖昧情境 |

---

#### 任務 B：環境安全度評分

**輸入**：攝影機截圖（單幀靜態圖）+ 攝影機位置與場所描述

**評分向度（總分 100 分）**：

| 向度 | 配分 | 評分說明 |
|------|------|---------|
| 地面與地板狀況 | 30 分 | 地面是否有積水、散落雜物、翹起的防滑墊或地毯捲邊 |
| 通道暢通性 | 30 分 | 主要走道是否有家具、推車、輪椅、設備等阻擋 |
| 潛在危險物品 | 20 分 | 是否有尖銳物、不穩固椅子、易翻倒的容器或雜物堆放 |
| 照明條件 | 20 分 | 光線是否充足、有無陰暗死角或強反光造成視線不良 |


**各向度評分等級對照**：

| 分數比例 | 等級 | 說明 |
|---------|------|------|
| 90-100% | 良好 | 無明顯風險 |
| 70–89% | 注意 | 輕微潛在風險，建議改善 |
| 40–69% | 警示 | 存在明顯危險因子，需盡快處理 |
| 0–39% | 危險 | 高度危險，應立即排除並限制長者進入 |

**結構化輸出（JSON）**：

```json
{
  "total_score": 72,
  "floor_condition": {
    "score": 20,
    "max": 25,
    "level": "注意",
    "description": "地面整潔，但走廊西側有一處防滑墊邊緣翹起"
  },
  "pathway_clearance": {
    "score": 20,
    "max": 25,
    "level": "注意",
    "description": "主走道暢通，但護理站旁有一台輪椅未歸位，略微佔用通道"
  },
  "hazard_objects": {
    "score": 16,
    "max": 20,
    "level": "良好",
    "description": "未見尖銳物或不穩固物品"
  },
  "lighting": {
    "score": 8,
    "max": 15,
    "level": "警示",
    "description": "走廊東側燈管故障，該區域照明明顯不足"
  },
  "safety_facilities": {
    "score": 8,
    "max": 15,
    "level": "注意",
    "description": "扶手完整，但走廊入口夜燈被椅子遮擋"
  },
  "overall_description": "整體環境尚可，主要風險在東側走廊照明不足與入口夜燈遮擋，建議盡快處理",
  "risk_factors": ["東側走廊燈管故障", "走廊西側防滑墊翹起", "入口夜燈被遮擋"],
  "score_drop": 12,
  "alert_needed": false
}
```

| 欄位 | 型別 | 說明 |
|------|------|------|
| `total_score` | int (0–100) | 本次總分 |
| `floor_condition` / `pathway_clearance` / `hazard_objects` / `lighting` / `safety_facilities` | object | 各向度分數、等級、文字描述 |
| `overall_description` | string | 整體環境的自然語言摘要（繁中） |
| `risk_factors` | string[] | 本次偵測到的風險因子列表 |
| `score_drop` | int | 與前次相比的分數下降量（由後端計算後回填） |
| `alert_needed` | boolean | 是否觸發提醒（score_drop ≥ 閾值） |

**設計重點**：
- 以固定向度確保分數跨時間可比性，避免 VLM 每次自由發揮導致無法計算趨勢
- 以 system prompt 明確指定評分標準，避免模型主觀判斷偏差
- `score_drop` 由後端在取得本次分數後與資料庫最新紀錄比對計算，再決定是否觸發提醒

### 5.3 冷卻機制設計

冷卻機制在初篩規則觸發後、事件建立前執行，防止同一跌倒事件被重複建立。

**雙層保護設計**：

```
YOLO 初篩「疑似跌倒」
        │
        ▼
[第一層：Track ID 冷卻查詢]
  ─ 查詢該 Track ID 是否在冷卻期內（預設 5 分鐘）
  ─ 是 → 抑制，不建立事件（COOLDOWN_SUPPRESSED，記錄 log 但不通報）
  ─ 否 → 繼續
        │
        ▼
[第二層：空間鄰近度保護]（應對 Track ID 漂移情境）
  ─ 查詢過去 5 分鐘內，倒地位置 bounding box 中心點距離 < 閾值 的事件
  ─ 有 → 抑制，視為同一事件（附註：可能為同人 ID 重分配）
  ─ 無 → 繼續
        │
        ▼
送入 VLM 複判
```

> <!-- NOTE: ByteTrack 短暫遮擋（< 2 秒）後通常可維持同一 Track ID；長時間離開畫面後重新進入會取得新 ID。第二層空間保護是為了覆蓋後者的情境，避免同一長者二次進入畫面的第一個動作被誤判為新跌倒事件。冷卻時間建議保守設定（5 分鐘），寧可有短暫漏報保護，也避免同事件被反覆通報造成 alarm fatigue。 -->

### 5.4 事件分級與狀態機

```
YOLO 初篩「疑似」
    │
    ├─ 冷卻抑制 ──→ COOLDOWN_SUPPRESSED（記錄 log，不進後續流程）
    │
    ▼
SUSPECTED（疑似，等待 VLM 複判）
    │
    ├─ VLM 判定跌倒 ──→ CONFIRMED（確認）
    │                         │ 定向通知照護員
    │                         ▼
    │                     NOTIFIED（已通報）
    │                         ├─ 照護員接手 ──→ ACKNOWLEDGED（已接手）
    │                         │                          │ 處理完成
    │                         │                          ▼
    │                         │                     RESOLVED（已結案）
    │                         │
    │                         └─ 逾時未接手 ──→ ESCALATED（已升級）
    │                                                    │ 處理完成
    │                                                    ▼

```

### 5.5 Agent 編排設計

Agent 是協調者：依事件狀態自主蒐集情境、推理、選擇工具，並對自己的把握度做路由。本節的設計原則是 **確定性護欄 + 有界自主（bounded autonomy）**——在安全攸關、不可逆的路徑上保持確定性規則與人工確認，在模糊、可逆、僅為草擬與排序的環節才開放 agentic 推理。能說清楚「哪裡刻意給自主、哪裡刻意不給、為什麼」本身即為設計成熟度的展現。

#### 5.5.1 自主邊界（Autonomy Boundary）

| 動作 | 自主程度 | 設計理由 |
|------|---------|---------|
| 對外通報家屬、送醫建議觸發 | **不自主**：僅草擬建議，人工於中控台確認後執行 | 不可逆且涉及人身安全，不容許 LLM 幻覺造成漏報或誤觸 |
| 逾時升級加派 | **半自主**：agent 提出升級提案與理由；逾時規則為確定性後盾，不論 agent 是否提案皆會觸發 | 升級可逆且有時間敏感性，但不能完全依賴 LLM 判斷是否該升級 |
| 蒐集情境、組裝 prompt、要求再確認一幀 | **完全自主** | 純讀取與推理，無外部副作用 |
| 誤報抑制的再判斷、派工排序、敏感度微調**提案** | **自主（可逆且留痕）** | 可逆、低風險，且所有調整均記錄供 MLOps 複查 |

> <!-- NOTE: 安全邊界 — send_to_hospital、notify_family 等動作不得由 agent 自動執行，僅能產生「建議」並由人工於中控台確認後觸發。逾時升級採「agent 提案 + 確定性規則後盾」雙保險，確保即使 agent 推理失效，安全網仍在 -->

#### 5.5.2 單一事件：ReAct 蒐集 → 推理 → 行動迴圈

跌倒初篩觸發後，agent 不是反射式直接呼叫 VLM，而是先**蒐集情境再組裝判斷請求**，形成多步的 observe → reason → act 迴圈：

1. **Observe（蒐集情境）**：調用 `query_camera_context`、`query_zone_context`、`query_trajectory`，取得該鏡頭今日誤報率、ROI 屬性（浴室／走道／活動室）、時段、軌跡型態（快速倒地後無位移 vs. 緩慢蹲下）
2. **Reason（組裝帶上下文的複判）**：將上述脈絡注入 VLM prompt，例如「凌晨 03:12、浴室區、軌跡顯示快速倒地後 8 秒無位移」，而非送出一張裸圖
3. **Act（依結果選擇後續工具）**：依 VLM 回傳的信心分數與分級進入 5.5.3 的路由
4. 必要時迴圈：若 VLM 回傳「資訊不足」，agent 可要求再擷取一幀或等待數秒觀察軌跡後重判

> <!-- NOTE: 蒐集情境僅使用 zone/ROI/軌跡等場域資訊，不引入生物辨識（已於 2.5 本期不做中排除） -->

#### 5.5.3 不確定性路由（Uncertainty-based Routing / Defer-to-Human）

Agent 對 VLM 複判信心分數分區處理，核心精神是「**知道自己不確定，就交給人**」：

| 信心區間 | 路由決策 |
|---------|---------|
| 高信心（≥ 0.85） | 確認事件，進入分流與通報流程 |
| 灰色地帶（0.5–0.85） | 三選一：①要求再擷取一幀／等待軌跡確認後重判　②建立事件但標記「低信心，待人工複核」並降級通知　③直接交人工判定 |
| 低信心（< 0.5） | 抑制為疑似誤報，記錄供回饋（不打擾值班人員，避免警報疲乏） |

#### 5.5.4 多事件 Triage（同時事件的派工推理）

當多個事件同時發生（兩區同時跌倒、或跌倒撞上久滯不動事件），agent 不採固定優先序，而是綜合 **信心分數、ROI 風險等級、已無人理會時長、值班表上最近可派人力**，推理出派工順序並輸出理由（供中控台顯示與事後復盤）。此為「派工排序」而非「是否施救」，安全上可承受 agent 自主。

#### 5.5.5 跨事件記憶與模式推理（連結資料飛輪）

Agent 維護情節記憶（episodic memory），對**累積狀態**而非單一幀推理：

- B 區今日第 6 次誤報 → 推論可能為鏡頭角度／光線問題 → 調用 `flag_for_mlops_review` 提交複查並提出敏感度微調提案（留痕、可回滾）
- 203 室本週第 3 次接近跌倒 → 調用 `generate_risk_summary` 生成風險摘要供照護團隊（銜接 FR-9 風險預測接口）

#### 5.5.6 工具清單（Tool Use）

#### 5.5.7 Agent 決策評估（黃金測試集）

Agent 的「決策」與感知模型分開評估，避免只測模型不測編排。建構一組情境黃金測試集，覆蓋：同時兩事件的 triage 排序、灰色信心的路由選擇、夜間浴室高風險脈絡、重複誤報的模式偵測等。每個案例標註「期望決策」，量測 agent 的路由／派工／升級決策正確率。此測試集同時作為 5.9 MLOps 迴歸測試的一部分，確保調整 prompt 或換模型後 agent 行為不退步。

#### 5.5.8 成本模型（Cost Modeling）

多步推理代表每事件多次 LLM 呼叫。文件須可回答：平均一個跌倒事件約 N 次 VLM／LLM 呼叫、約多少 token、對應推論延遲與成本，以及「為何此成本換來的誤報下降與決策品質提升值得」。蒐集情境階段以本地廉價查詢（DB／快取）為主、僅在必要時呼叫 VLM，以控制每事件成本。

#### 5.5.9 併發優先序

- 收到跌倒初篩事件 → 啟動上述 ReAct 迴圈（高優先序，可中斷／插隊環境評分排程）
- 收到環境評分排程觸發 → 檢查 VLM 是否正處理跌倒複判中；若是則本輪評分延後至下一排程週期重試，不阻塞即時任務

#### 5.9.2 監控指標定義

| 指標 | 計算方式 | 監控頻率 | 注意條件 |
|------|---------|---------|---------|
| 每日誤報數（FP/Day） | 被標記誤報事件數 / 天 | 每日統計 | 連續 3 天超過基準值 |
| 信心分數平均值 | 所有 YOLO 初篩事件信心分數平均 | 每日統計 | 連續 7 天下滑趨勢（Model Drift 訊號） |
| VLM 推翻率 | SUPPRESSED 數 / 送入 VLM 總數 | 每週統計 | 超過 40%（代表 YOLO 初篩過度誤觸） |
| Hard Negative Pool 累積量 | 資料庫中未用於訓練的標記總數 | 每週統計 | 累積 ≥ 100 筆時於 MLOps 面板提示管理者 |

以上指標顯示於中控台 MLOps 面板，管理者可依趨勢判斷是否啟動 fine-tune。

#### 5.9.3 MLflow 整合方式

MLflow 以獨立 container 加入 Docker Compose，對外提供 Web UI，後端透過 MLflow Python SDK 操作。

**承擔職責**：
- **實驗追蹤**：每次 fine-tune 記錄訓練資料量、超參數（epochs、learning rate、batch size）、評估結果
- **模型版本管理**：Staging → Production 審核流程，保存每版 `.pt` Artifact
- **比較視圖**：並排比較不同版本的 Recall / FAR / mAP，輔助管理者決策

**Docker Compose 新增 container**：

```yaml
mlflow:
  image: ghcr.io/mlflow/mlflow
  ports:
    - "5000:5000"
  volumes:
    - ./mlflow-data:/mlflow
  command: mlflow server --host 0.0.0.0 --backend-store-uri sqlite:///mlflow/mlflow.db --default-artifact-root /mlflow/artifacts
```

#### 5.9.4 模型評估門檻（部署前必須通過）

Fine-tune 後的新模型在固定測試集上必須同時通過以下三項，才允許由管理者升格至 Production。

| 指標 | 門檻 | 說明 |
|------|------|------|
| Recall（召回率） | ≥ 現行 Production 版本 | 不允許漏報率上升 |
| False Positive Rate | ≤ 現行版本 × 1.1 | 誤報率惡化不超過 10% |
| mAP@0.5 | ≥ 0.75 | 基本偵測品質下限 |

**固定測試集組成**：
- 正樣本：自演跌倒影片（各種角度、光線條件）
- Hard Negative：坐地、伸展、彎腰、攙扶等曖昧情境

> <!-- NOTE: 固定測試集建立後即凍結（不隨 Hard Negative Pool 更動），確保跨版本比較的一致性。Hard Negative Pool 的新增資料用於訓練，不混入測試集。 -->

#### 5.9.5 Fine-tune 觸發與完整流程

本期採**人工觸發**；架構預留自動觸發接口，未來可接閾值判斷，不影響現有流程。

**觸發時機（管理者觀察後決定）**：
- Hard Negative Pool 累積 ≥ 100 筆新標記
- 近 7 天每日誤報數持續超過基準值
- 信心分數平均值出現連續下滑趨勢
- 管理者主動決定

**完整流程**：

```
[管理者在 MLOps 面板確認觸發]
        │
        ▼
匯出 Hard Negative Pool
+ 合併原始訓練資料集
        │
        ▼
執行 YOLOv8 Fine-tune
（手動腳本或排程任務）
        │
        ▼
MLflow 記錄實驗結果
上傳模型至 Model Registry（狀態：Staging）
        │
        ▼
在固定測試集上自動評估
        │
   ┌────┴────┐
 通過門檻   未通過門檻
   │            │
   ▼            ▼
管理者於 MLflow   保持現有 Production 版本
Web UI 審核確認   記錄失敗原因
   │
   ▼
切換 Production
（舊版本狀態改為 retired，保留可回滾）
   │
   ▼
[若新模型上線後效能劣化]
   ↓
一鍵回滾至上一個 Production 版本
```

**彈性預留（後續工作）**：
當「Hard Negative Pool 累積量」或「每日誤報數」超過設定閾值，系統自動觸發資料匯出與 fine-tune 腳本，人工只需做最後的評估確認與部署審核，不改變流程結構。

## 7. 期末展示規劃（Demo Plan）

### 7.1 展示策略與原則

- **主敘事對齊 2.1 三支柱**：開場定位為「human-in-the-loop agentic 照護編排系統」，跌倒辨識是其中一個感知輸入，避免被歸類為「又一個跌倒偵測 demo」
- **能即時就即時、會出包就預錄**：穩定且有張力的環節走現場（曖昧情境抑制、即時閉環）；無法即時或風險高的環節走預錄或半預錄（fine-tune、逾時升級壓縮計時）
- **每個技術點配一句 takeaway**：講評委聽得懂的「所以呢」，例如「它知道自己不確定，就交給人」
- **地端離線可跑**：全程不依賴外網，避免現場網路風險（同時也是隱私架構的活證明）

### 7.2 值得展示的技術點（依展示價值排序）

### 7.3 建議展示動線（8–10 分鐘）

1. **痛點與定位（1 分）**：超高齡照護痛點 → 一句話定位（三支柱）

- **固定片段集**：使用一組驗證過、穩定可重現的測試影片，不臨場找素材
- **計時壓縮**：逾時升級的 timeout 在 demo 模式設為數秒，避免乾等
- **離線運行**：全程地端，不依賴外網
- **彩排門檻**：整合凍結（07/28）後即開始端到端彩排，08/04–08/08 專做錄製與 buffer
