## 4. 事件列表卡片 — 必要資訊（無點擊狀態）

### 必須顯示

| 欄位 | 原因 |
|------|------|
| 事件類型 | 六大模組哪一種，直接影響反應方式 |
| 地點／房號 | 值班人員要知道往哪裡去，非僅攝影機編號 |

| 目前狀態 | NOTIFIED／ACKNOWLEDGED／ESCALATED，色彩區分 |
| 信心分數／嚴重度 | VLM 二審後分數，輔助判斷誤報機率 |

### 建議加（可再省一次點擊）

| 欄位 | 原因 |
|------|------|
| 事件快照縮圖 | 比文字描述更快確認「有沒有事」 |

### 不建議放在卡片表面

完整事件描述、VLM 完整報告、歷史軌跡 — 留給點擊後的詳情頁。

## 7. 事件通知分級機制（二階段設計）

### 決策脈絡

最初提案為三層（toast → 全螢幕 → 佇列），經確認**事件發生頻率不高、中控站為專用監看設備**後，簡化為二階段，分界點設在「系統是否已確認需要人工介入」，而非用頻率作主要判斷依據。

### 階段一｜系統判斷中（VLM 複審前）

- **不推送文字通知**，僅在畫面角落顯示會動的小圖示 + 數量角標
- 原因：此階段觸發頻率等同六大模組偵測頻率，遠高於真正需要人介入的事件頻率，逐筆推播文字等同把系統內部雜訊丟給人腦處理
- 點擊角標才展開輕量清單，清單僅列**地點**，不寫完整句子（因為這階段本來就可能是誤報）

### 階段二｜系統已確認，需人工介入

- **直接觸發大面積警示（約佔螢幕 78% 寬）**，中間不經過任何緩衝的小卡片階段
- 警示卡內容：狀態標籤、事件標題、快照、信心分數、經過時長、操作按鈕（確認前往處理／呼叫協助）
- 需**主動按下「確認前往處理」才能關閉**，不可自動消失
- 保留區分「判斷中」與「已確認」兩種狀態的原因：若所有事件都用同一種呈現方式，大面積警示會失去「這件事特別重要」的訊號意義，久了中控人員會用同一種心態應對所有大畫面，降低對真正嚴重事件的警覺度

### 多筆事件同時發生（低頻率但需保留）

- 主警示卡維持單一焦點（78% 寬），下方保留窄佇列列出其他「已確認」事件的縮影
- 佇列僅在真正同時有多筆已確認事件時出現，不影響日常單筆事件的體驗
- 實作提醒：警示卡跳出時若中控人員正在填寫其他事件的處置記錄，需確保該筆資料不因彈窗而遺失，回來後可接續（非線框圖範圍，提醒工程端注意）

### 流程示意

```
偵測觸發
  │
  ▼
系統判斷中（VLM 複審中）
  │  畫面角落小圖示 + 角標數字，不打斷
  │  點擊角標 → 展開輕量清單（僅地點）
  │
  ├─ 判定非事件 ──→ SUPPRESSED，角標數字 -1，無其他動作
  │
  └─ 判定需人工介入 ──→ 直接觸發全螢幕警示（78% 寬）
                             │
                             ├─ 單筆 → 全螢幕警示，無佇列
                             │
                             └─ 同時多筆 → 主警示卡 + 下方待處理佇列
                                             （點佇列項目切換至該筆警示）
```

## 8. 歷史紀錄頁（IA 7. 對應）

### 8.1 原圖問題：4 個子節點只做了 1 個

IA 定義歷史紀錄底下有 4 個子節點，原圖用一個下拉選單「案件通報記錄＜選單＞」暗示可切換內容，但切換邏輯不明確：

| 節點 | 說明 | 原圖狀況 |
|------|------|---------|
| 7-1 事件歷史 | 全部事件的可篩選查詢（跨狀態、跨時間） | 未獨立呈現 |
| 7-2 環境安全評分歷史 | 全部攝影機評分歷史查詢 | 未獨立呈現 |
| 7-3 通報紀錄 | Web Push 發送紀錄（channel／status／sent_at） | 對應原圖「案件通報記錄」，但只用下拉選單帶過 |
| 7-4 影像片段下載 | 事件影片／環境截圖下載管理，含保存期限標示 | 未獨立呈現 |

**調整**：下拉選單改為頁籤（tab），4 個子節點各自一個頁籤，與事件中心／環境安全頁的分頁邏輯一致。本輪僅完成「通報紀錄」頁籤的卡片細節，其餘三個頁籤列入待辦。

### 8.9 討論並否決：總覽頁改顯示平均分

**提案**：總覽頁卡片改顯示一段時間平均分，詳細單筆記錄移至歷史紀錄頁查看。

**否決原因**：IA 4-1 明確定義為「**最新**總分卡片」（`GET /env-scores/latest`），且 FR-6.4 異常提醒是拿「本次」對比「前一次」單筆分數觸發，非平均值。若總覽頁改顯示平均分，會出現「危險標籤」與「平均分數字看起來還好」互相矛盾的畫面，使用者需自行解讀矛盾，反而增加認知負荷。

### 8.10 環境評分歷史（7-2）聚合規則定案：用最低分，不用平均分

延續 8.9 節「不能用平均掩蓋危險訊號」的原則，套用到歷史頁的長區間聚合：

| 查詢區間 | 顯示粒度 |
|---------|---------|
| ≤ 24 小時 | 原始 15 分鐘級距，不聚合 |
| 1–7 天 | 每小時最低分 |
| > 7 天 | 每日最低分 |

理由：本頁功能定位為「稽核用，供管理者與家屬查閱佐證」（IA 第 7 節），用平均分會讓曾經跌到危險又被處理回穩的當天看起來像普通的一天，等於把該被看見的風險訊號稀釋掉，違背稽核頁面的用途。聚合後的資料點沿用既有色彩語言（危險紅／警示橘）標示，與 11.4 節「趨勢圖與異常提醒紀錄同頁」的既有決策一致。底下逐筆資料表不受影響，維持顯示原始紀錄（靜態分頁，見 8.5 節）。

**參考依據**：`Fulilian_IA資訊架構_v1.md`（第 7 節歷史紀錄功能說明、4-5 異常提醒紀錄）、本文件 8.9 節、11.4 節。

### 8.12 釐清：zone_name 並非真實資料庫欄位，改為 location 衍生顯示

**發現**：先前設計假設 `devices.location` 與環境安全頁 `zone_name` 是兩份需要同步的資料，經查證後發現 `devices` 表僅有 `location` 一個位置欄位（`CareLoop_協作文件_v1_6.md` 5.6 節），並無獨立 `zone_name` 欄位。原本擔心的「兩份資料不同步」問題前提不成立，因為只有一份真實資料。

**解法（不需異動後端）**：環境安全頁顯示的區域名稱，不另外儲存，改為讀取時直接從 `devices.location` 衍生（前端顯示邏輯切分文字），要求裝置管理（8-1）填寫 `location` 時維持固定格式慣例（如「走廊A・302房外側走道」）即可，不需新增欄位、不需同步機制。

**待確認（尚未定案，需後端確認）**：8-2 區域管理定義 Zone 為獨立設定項目（供 `query_zone_context` 使用），但 `devices` 表目前無對應外鍵，不清楚裝置與 Zone 的關聯是否應為正式結構化資料。若是，僅靠 `location` 文字切分可能不足以長期支撐；需後端確認 Zone－裝置關聯的真實存在形式。

**參考依據**：`CareLoop_協作文件_v1_6.md`（5.6 資料庫設計、5.5.6 工具清單 `run_env_assessment`）、`Fulilian_IA資訊架構_v1.md`（8-2 區域管理）。

### 8.13 後端已建立 location 正式關聯表，但尚未支援樓層分組

**進展**：後端依 8.12 節討論方向，已將 `devices.location` 自由文字欄位改為正式關聯：新增獨立 `location` 表（`location_id` 主鍵＋名稱欄位），`devices` 新增 `location_id` 外鍵（n 對 1）。解決原本「無正式歸屬關係」的問題。

**尚未達成**：`location` 表目前僅有名稱一個欄位，仍是單一層級清單，沒有樓層維度，無法直接支援樓層分組。

**建議（待後端確認）**：在既有 `location` 表新增兩欄即可，不需另建新表：`floor`（樓層文字，如「2F」「B1」）、`floor_order`（樓層排序數值，避免「B1」用字母排序被排到中間，見《攝影機選擇器_樓層分類vs攝影機分類_討論文件.md》）。

**參考依據**：使用者提供之後端 ER 圖（devices ↔ location 關聯）、8.12 節、《攝影機選擇器_樓層分類vs攝影機分類_討論文件.md》。

### 8.14 討論：樓層欄位放同一張 location 表的正規化風險

**問題**：8.13 節建議的 `floor`／`floor_order` 直接加在 `location` 表，會讓同一樓層的多筆地點資料重複存同樣的樓層與排序值（如走廊A、走廊B、浴室B同在2F，三筆都要填一樣的值），存在資料不一致風險（改了一筆忘記同步其他筆）。

**兩個選項**：①維持加在同一張表（改動小，但有上述重複風險）；②另拆 `floors` 表，`location` 表用外鍵關聯（資料正規，但多一張表、多一次查詢）。

**暫定判斷**：考量 `CareLoop_協作文件`既有架構決策（本地／edge-ready、MVP 精簡原則）與機構樓層數量通常個位數，風險與影響範圍小，傾向接受選項①，但最終由團隊決定，非定案。

**參考依據**：`CareLoop_協作文件_v1_6.md`（部署架構決策：本地／edge-ready，MVP 無需 K8s）。

### 8.15 推翻：floor 不用 ENUM，改為獨立 `floors` 表（呼應組員補充）

**原決策(已推翻)**：`floor` 曾定案採用 ENUM 型別。

**推翻原因**：組員指出樓層可能包含「夾層」「RF」「中庭、戶外」等無法事先窮舉的類型；且使用者提供之後端 ER 圖顯示 `devices` 表有 `company_id` 外鍵，暗示系統可能為多租戶架構——若為多租戶，ENUM 這種資料庫層級全域共用的型別定義會讓不同機構的樓層選項互相污染，問題比單純「新增樓層要改結構」更嚴重。

**新定案**：新建 `floors` 表（`floor_id`、`floor_name` 自由文字、`floor_order` 排序數值，多租戶則加 `company_id`），`location` 表原本的樓層欄位改為 `floor_id` 外鍵。理由與 8.24 節否決區域用 ENUM 的邏輯一致：凡是 admin 會自行管理、不同場域內容可能不同的清單，都不該用 ENUM，該用獨立資料表。這樣可同時達成：①樓層名稱不受限（含夾層／RF／中庭等）；②排序數值只存在 `floors` 表一處，不會像純字串輸入那樣在多筆 `location` 資料裡重複打字、可能兜不起來；③多租戶下各機構樓層清單互不干擾。

**對前端無影響**：攝影機選擇器、區域選擇器的「樓層分組收合」畫面呈現方式（8.16、8.23、13.2 節）不需更動，僅背後資料來源從 ENUM 換成獨立表，使用者操作體驗不變。

### 8.27 後端回覆：floor 僅給一欄可空值欄位，取消樓層分組層

**後端回覆**：目前用不到 8.15 節提議的 `floors` 表，僅在 `location` 表給一欄可空值的樓層欄位，近期不會積極填寫，留待未來需要時再用。

**影響**：先前 8.16、8.23、13.2 節設計的「樓層收合分組」皆假設樓層資料完整可靠；欄位可空值且近期資料稀疏，分組會出現空群組或大量未分類項目，體驗劣於不分組。

**修正（推翻樓層分組層）**：選擇器結構退回兩層——直接以「區域」（必填、永遠可靠）分組列出攝影機，不再有樓層收合層。樓層資料退化為顯示文字的選填加分項：有填則附加於文字（如「鏡頭3・2F」），未填則不顯示，畫面不受樓層填寫進度影響，無論目前資料量多寡都不會出現空群組。8.16、8.23、13.2 節提及之樓層分組畫面自本節起以此為準。

### 8.28 Demo 資料範圍：company／floor 皆固定為 1

**假設**：Demo 資料統一假設 `company_id=1`、樓層固定為 1（單一租戶、單一樓層），僅供展示用，非正式資料規模。

### 8.18 原始紀錄表裝置資訊：不另開欄位，併入評分時間下方小字

**問題**：先前兩版線框圖欄位數量不一致（正常版 4 欄，離線版多一欄「裝置」），若正式採用會讓表格結構隨情境變動，造成使用者困惑。

**定案**：不新增獨立「裝置」欄位，改為「評分時間」欄位下方加一行小字顯示裝置名稱。正常情境下每列重複同一裝置名稱，字小、色淡，可自然略過；離線／裝置更換情境下，小字內容改變（如「鏡頭3.1」「鏡頭3（已停用）」），靠內容變化本身吸引注意，不需額外欄位或標記機制。兩種情境欄位結構維持一致（4 欄），避免表格因情境不同而跳動。

### 8.19 總覽頁需排除「已停用」裝置，與「離線」區分處理

**發現**：8.17 節新增的「已停用」裝置概念（故障更換新機後，舊裝置永久不再回傳資料），與 11.2／11.7 節既有的「離線」設計（暫時性，等待修復）是兩個不同概念，總覽頁原設計未考慮「已停用」的情況。

**問題**：若已停用裝置繼續以「離線」卡片顯示於總覽頁「需要注意」區塊，會變成永遠卡住、無人需處理卻不會消失的卡片，違背該區塊「值班待辦清單」的定位。

**建議**：總覽頁「各攝影機最新總分卡片」查詢應排除已停用裝置；暫時離線維持既有「離線」卡片顯示，已停用則直接從清單移除，新裝置上線後以全新卡片呈現。

**待確認（需問後端）**：`devices.status` ENUM 是否已區分「離線」與「已停用」兩種狀態，或需另加欄位（如 `is_retired`）區分暫時性與永久性狀態。已整理為團隊提問格式，待後端回覆。

**參考依據**：本文件 11.2 節、11.7 節、8.17 節。

### 8.20 勘誤：影像片段下載表格「地點・事件」欄位格式不一致

**問題**：事件影片列填簡稱地點（如「走廊A」），環境截圖列填完整攝影機格式（如「2F・走廊A・鏡頭3」），同一欄位下兩種格式並存；環境截圖本無事件類型可填，但欄位標題「地點・事件」暗示每列都該有事件類型，造成不必要的困惑。

**修正**：攝影機位置統一採 8.16 節格式（樓層・區域・攝影機），不分內容類型；事件類型獨立成一欄，環境截圖列直接以「—」呈現，不強行填充。

### 8.21 釐清：事件類型欄位定義、新行為分類機制

**釐清**：先前線框圖將「事件類型」顯示為「疑似跌倒」，實為 `status`（疑似）與 `event_type`（跌倒，目前唯一值，見 5.6 節 events 表）兩欄混合顯示，非單一欄位。真正會分類的是「誤報類型」（`hard_negative_pool.label`，固定清單：坐地／伸展／彎腰／攙扶／其他，見 FR-7.2）。

**新行為分類機制（非模型自動學習）**：VLM 輸出為結構化格式，分類選項於系統開發階段寫死在 prompt 中，模型僅能從既有選項選擇，不會自行創造新分類。遇到清單外的行為，流程為：①照護員當下選「其他」＋文字備註（FR-7.2 `note` 欄位）；②累積於 Hard Negative Pool（6-2 節）供團隊人工檢視；③若規律重複出現，由團隊決定是否正式新增分類，並於下次 fine-tune（6-4 節）納入訓練。全程需人工判斷與介入，非即時自動化。

**影像片段下載表格不受影響**：離線／裝置更換與事件類型分類為互不相關的兩個維度，無需特別處理；離線期間本來就不會產生任何新影片或截圖（延續 11.2 節原則）。

### 8.22 影像片段下載表格：「事件類型」改為「狀態」

**問題**：event_type 永遠只有「fall」一個值（8.21 節已釐清），放在表格欄位裡每列皆相同，不提供任何可辨識資訊，屬於無效欄位。

**修正**：欄位改為「狀態」（已結案／已升級／誤報），沿用事件歷史頁籤既有狀態標籤樣式；誤報事件另加一行小字顯示誤報子分類（坐地／伸展／彎腰／攙扶／其他，FR-7.2），非誤報事件不顯示。環境截圖仍以「—」呈現（無狀態概念）。

### 8.23 統一用詞為「區域」，定義事件歷史／影像片段下載的篩選層級

**問題**：先前「影像片段下載」篩選列用詞為「地點」，與 IA 8-2「區域（Zone）管理」及本文件 10.4 節既有用詞「區域」不一致，屬同一概念、用詞落差。

**修正**：統一改為「區域」。

**定案**：事件歷史／影像片段下載的區域篩選，樓層分組後僅到「區域」層級（如「走廊A」），不像 8.16 節環境評分歷史的攝影機選擇器需再往下選到個別攝影機。原因：評分本身以單一攝影機為最小單位（11.2 節），查詢須精準；但事件／影片瀏覽情境是概略查看某區域是否有事，選一個區域即可帶出底下全部攝影機的相關資料，不需先指定攝影機。選項資料沿用既有 `location` 表（8.13、8.15 節），無需新增資料來源。

### 8.24 釐清：區域不適用 ENUM，維持獨立資料表

**問題**：討論是否比照 8.15 節樓層 ENUM 的做法，將「區域」也改用 ENUM。

**否決**：區域與樓層變動頻率完全不同。8-2 區域管理定位為 admin 日常自助設定項目（機構擴建、重新規劃時新增區域），若改 ENUM，新增區域需改資料庫結構、重新部署，會讓自助式設定頁功能失效，違背 8. 設定頁「僅 admin 可操作、不需工程師介入」的定位。

**結論**：維持現況，區域用獨立 `location` 表（後端既有實作已正確），僅樓層沿用 ENUM。

**參考依據**：`Fulilian_IA資訊架構_v1.md`（8-2 區域管理、8. 設定頁定位）、本文件 8.13、8.15 節。

### 8.25 影像片段下載補強：狀態篩選、即將到期快速切換、批次下載

**問題**：IA 特別強調保存期限需醒目標示，但原設計只做到視覺顯示，未提供對應篩選能力，無法快速找出待下載的即將到期項目。

**新增**：①狀態篩選（已結案／已升級／誤報），沿用 8.22 節既有標籤樣式；②「只顯示即將到期」快速切換，沿用保存期限既有紅色警示樣式；③勾選框＋批次下載按鈕，僅需要時使用，不影響原單筆下載操作。三者皆延伸既有資料與視覺語言，未新增資料庫欄位。

### 8.26 影像片段下載補強：全選勾選框、類型欄位改回中文文字

**新增**：表格標題列加入母控制勾選框（全選／取消全選／部分選取三態），點擊即可批次勾選所有列，簡化多筆下載的操作步驟。

**修正**：8.25 節示意曾將「類型」欄位簡化為純圖示，經檢視單靠 icon 需使用者記憶圖示對應意義，反而增加認知負荷；修正為圖示＋中文文字並列（如「事件影片」「環境截圖」），文字為主要辨識依據，圖示僅輔助。

**確認**：區域篩選操作方式維持 8.24 節既有設計（樓層分組收合、點擊區域後選定並收合面板），無變更。

## 9. 即時監控頁（IA 2. 對應）

### 9.1 節點範圍

| 節點 | 說明 | 對應章節 |
|------|------|---------|
| 2-1 攝影機清單 | 依區域（zone）分組列出所有攝影機，顯示上下線狀態 | FR-1.1 |
| 2-2 即時畫面 | 單路即時串流播放 | FR-1.1、4.4 |

| 2-4 Debug 監控 🔒 | 規則初篩分數、冷卻狀態、Track ID，僅 admin 可見，供開發除錯用 | FR-1.4、1.5、5.3 |

### 9.2 總覽版面：依區域分組的攝影機牆

- 比照 IA「依 zone 分組」，以區域為單位（如走廊 A、浴室 B、活動室）分段呈現攝影機縮圖
- 每張縮圖顯示上下線狀態點；離線鏡頭降低透明度並標示「離線」
- 正在偵測到疑似事件的鏡頭，縮圖直接加紅框＋「偵測中」標籤，不需點進去才知道哪一路異常

### 9.3 單路詳情：持續疊加 vs 事件觸發疊加，兩者觸發時機不同

這是本輪釐清的關鍵點，避免誤解成「只有偵測到疑似事件才出現疊加畫面」：

| 內容 | 出現時機 |
|------|---------|
| 骨架關鍵點／追蹤框本身 | **持續疊加**，只要畫面上有人被系統追蹤到就會顯示，因為姿態估測與多目標追蹤（FR-1.2、1.3）是逐幀運作的底層機制，不是事件觸發才啟動 |
| 「疑似跌倒」紅框標籤 | 只有規則初篩判定為疑似時才**額外**標示 |
| Debug 面板（Track ID、冷卻狀態、規則初篩分數） | 同樣是**持續存在**，只要該路鏡頭有人被追蹤，這些數據就存在；不是「偵測到才生出面板」，而是「面板一直都在，內容會隨追蹤狀態即時變動」 |

**結論**：點擊任一路攝影機都會放大進入同一套版面（含 Debug 面板，若為 admin 身份）；不存在「平常一種版面、偵測到事件才切換成另一種版面」的差異。差別只在於：畫面上有沒有出現額外的紅框標籤，以及 Debug 面板裡的數字內容當下是什麼。

### 9.4 Debug 監控與 MLOps 面板的界線

Debug 監控（2-4）與 MLOps 面板（6.）容易被誤認為同一類，需要明確區分：

| 比較項目 | Debug 監控（2-4，即時監控底下） | MLOps 面板（6.） |
|---------|------------------------------|-------------------|
| 時間尺度 | 當下這一幀、這個 Track ID 的即時狀態 | 模型過去一段時間的整體效能趨勢 |
| 對象 | 單一攝影機、單一追蹤目標 | 跨事件、跨時間彙總的模型治理資訊 |
| 對應章節 | FR-1.3～1.5、**SDS 5.3 冷卻機制設計** | FR-8.1～8.7（效能監控、MLflow、fine-tune 觸發、版本回滾） |

**Track ID／冷卻狀態／規則初篩分數不搬進 MLOps 面板**，維持在即時監控頁的 Debug 面板內。若混入 MLOps 面板，會讓「模型治理」頁面混進即時性資料，模糊 MLOps 面板原本的資料飛輪定位。

Debug 面板具體對應 **SDS 5.3 冷卻機制設計** 的雙層保護流程：

```
YOLO 初篩「疑似跌倒」
  → 第一層：Track ID 冷卻查詢（是否在 5 分鐘冷卻期內）
  → 第二層：空間鄰近度保護（因應 Track ID 漂移，倒地位置 bounding box 中心點距離比對）
  → 送入 VLM 複判
```

> 技術備註（SDS 5.3 原文）：ByteTrack 短暫遮擋（< 2 秒）通常可維持同一 Track ID；長時間離開畫面後重新進入會取得新 ID。第二層空間保護即為覆蓋後者情境，避免同一長者短暫消失又出現時，第一個動作被誤判為新跌倒事件。

### 9.5 權限邏輯

- Debug 面板僅 admin 可見；staff 登入時**完全不渲染**該區塊，不是灰階顯示，避免佔用版位或造成困惑
- 一般照護員（staff）看到的單路詳情頁，只有畫面本身＋事件疊加，沒有 Debug 面板

### 11.2 關鍵釐清：評分單位是「攝影機」，不是「區域」

這是本輪最重要的修正。IA 明確定義 4-1 為「**各攝影機**最新總分卡片」，SDS 5.2 任務 B 的輸入也是「攝影機截圖＋攝影機位置描述」，評分的最小單位是**單一攝影機**，不是區域平均。

- 初版線框圖誤把卡片標題畫成區域名稱（如「走廊 A」代表一整區），容易被誤解為多台攝影機平均分數，已修正為逐攝影機呈現（如「走廊 A · 鏡頭 1／鏡頭 2／鏡頭 3」各自獨立卡片），與即時監控頁（2-1）的攝影機命名方式對齊
- 「平均分」這個概念只出現在 **Home 首頁的 KPI 卡片**（IA 1. 定義：「各攝影機最新評分平均值」），環境安全頁本身不做區域彙總，只呈現逐攝影機原始分數
- 離線中的攝影機（無法評分）需要獨立的卡片狀態（「離線，無法評分」），不能留空或誤植為 0 分

### 11.3 總覽頁設計（v2 修訂：不對稱版面）

初版曾嘗試「逐攝影機一致大小卡片」與「平面圖檢視」兩種方案，皆已捨棄：

- **逐攝影機一致卡片**：每台攝影機佔用相同版面，但「正常」攝影機不需要那麼多空間，版面效率不佳
- **平面圖檢視**：需要建築座標資料，IA 設定頁（8-2 區域管理）目前未定義攝影機座標欄位，且經確認不採用此方向

**最終採用：不對稱版面，依是否需要注意分兩層呈現**

| 分層 | 呈現方式 | 內容 |
|------|---------|------|
| 需要注意（警示／危險等級） | 大卡片，置頂 | 攝影機名稱、分數、等級標籤、**主要風險摘要**（一行文字，取自既有 risk_factors，非新增欄位）、迷你走勢長條圖 |
| 正常（良好／注意等級，含離線） | 一行式精簡列表 | 攝影機名稱、狀態色點、**趨勢箭頭**（↑／↓／—，僅表示方向不表示幅度）、分數（離線顯示「離線」取代分數） |

設計原則：
- 版面空間分配跟着「是否需要處理」走，不是每個項目平均分配版面
- 新增的「主要風險摘要」只出現在需要注意的卡片上，正常項目不加這行文字，避免均勻堆疊資訊反而稀釋掉真正重要的部分
- 趨勢箭頭刻意做得極簡（單一符號＋方向色，不做迷你走勢圖），因為完整走勢圖的視覺重量會跟「正常、不需特別注意」的訊息矛盾；完整走勢留給評分詳情頁（4-4）呈現
- 頁面頂部維持原本「危險區域」提示條，作為最上層的摘要入口

### 11.4 評分詳情頁設計

- 五向度分項分數以進度條呈現，各自標示分數／滿分／等級
- 整體描述（overall_description）與風險因子（risk_factors）以標籤呈現
- 整合 4-4 評分趨勢（近期折線圖）與 4-5 異常提醒紀錄（score_drop 事件列表）於同一頁，不另外分頁

### 11.5 待確認：評分向度權重的文件矛盾

CareLoop_協作文件_v1_6 內部存在資料矛盾：

- 「評分向度」表格只列 4 項（地面 30 分／通道 30 分／危險物品 20 分／照明 20 分＝100 分），拿掉了「安全設施完整性」向度
- 但同一份文件的 JSON 結構化輸出範例仍保留 `safety_facilities` 欄位（15 分），權重總和沿用舊版 25/25/20/15/15

本輪線框圖暫時採用 **5 向度、25/25/20/15/15**（沿用 JSON schema 與舊版權重）畫出進度條示意，實際向度數量與權重需與團隊確認 v1_6 是否為有意刪減，待確認後再回來調整詳情頁的分項數量與比例。

### 11.6 需要注意卡片：走勢呈現改版（折線＋閾值線，並依等級分流）

#### 決策脈絡

初版「需要注意」大卡片以迷你走勢**長條圖**呈現近 7 筆 `score_history`。討論後認為長條圖的視覺語言偏向「分類比較」，在迷你尺寸下容易把連續 7 天的資料切成一格一格，反而稀釋掉「持續下滑」這個最重要的訊息；折線圖能以連續線條直接傳達趨勢方向，且比長條更省水平空間。

#### 改版一：走勢圖畫法

由長條圖改為「折線＋危險閾值虛線＋每日等級色點」：

- 折線本身傳達分數走勢的連續形狀
- 疊加一條危險閾值虛線，並將閾值以下的區域淡紅底標示，讓「是否跌破安全線」不需細看數字即可判斷——這是環境安全評分場景中最關鍵的操作性資訊
- 每個資料點依當日 `level` 上色（良好＝綠／注意＝灰／警示＝橘／危險＝紅），保留原本長條圖逐日看等級的優點

#### 改版二：卡片內部依危險程度再分流呈現方式

進一步比較後發現，若「需要注意」內的危險卡與警示卡都放同樣份量的走勢圖，會讓危險與警示的視覺重量再度拉平，違背原本刻意用資訊密度落差引導視線的設計原則（呼應第 11.3 節已捨棄「逐攝影機一致卡片」的理由）。因此在「需要注意」內部再分兩層：

| 等級 | 走勢呈現 | 說明 |
|------|---------|------|
| 危險 | 保留完整走勢圖（折線＋閾值虛線，末端資料點標色），圖下加一行文字提示（如「近 7 日降 43 分」） | 圖形＋文字雙重確認，危險等級承載最多資訊 |
| 警示 | 不放走勢圖，改為分數旁一個趨勢箭頭＋一行文字提示（如「較昨日降 8 分」） | 排版樣式與「正常」列表的箭頭一致，但額外補一行文字量化變化幅度，避免純符號不夠直觀 |

> 待確認：文字提示目前採「與前一筆評分相比」的變化量（如「較昨日降 8 分」），需與 `alert_history` 內 `score_drop` 的計算基準（是否固定為近一次評分比對）對齊，避免文字提示與異常提醒紀錄的定義不一致。

### 11.7 離線攝影機改歸類至「需要注意」區塊

#### 原始設計與疑慮

初版依 IA 規格「『正常』區塊（level = 良好或注意，**含離線**）」，將離線攝影機放入正常列表，僅將狀態色點改為灰階、分數位置改顯示「離線」文字。討論中提出疑慮：離線代表**完全的監控死角**，其急迫性可能不亞於、甚至高於警示等級——警示／危險至少系統仍在監控、已知具體風險項目；離線則是「不知道現況」，長者在該區域發生任何事都不會被偵測到。

#### 決策：離線移入「需要注意」區塊

比較過「離線移入需要注意」與「離線留在正常但提高醒目度（如整行套用危險色底）」兩種畫法後，採用前者，理由如下：

- **認知負荷**：若在「正常」列表中用高對比色標示離線那一行，會讓同一份列表混雜兩種判讀邏輯（多數行為「安靜、無需處理」的灰階，突然一行變成「立即處理」的紅色），使用者的視覺掃視習慣被打斷，畫面觀感也顯得混亂
- **行動急迫性一致**：離線需要處理（修復連線）與警示／危險需要處理（排除環境風險）在「值班人員該不該去處理」這件事上屬於同一層級，只是處理內容與負責對象不同；歸入同一區塊可讓值班人員一次掃過去拿到完整待辦清單
- **與正常區塊的語意切割**：離線移出後，「正常」區塊只剩良好／注意兩種狀態，判讀邏輯單純化為「這些都不用管」，不再需要在一堆安靜的灰色列裡分辨哪一行其實是特殊狀態

#### 呈現方式

離線卡片與危險、警示卡片並列於「需要注意」區塊，但刻意做出區隔，避免被誤認為「已知環境風險」：

- 左側色條改用中性灰（`text-muted`），不使用紅／橘等風險色
- 等級標籤文字為「離線」，樣式為空心外框，非填色色塊
- 不顯示分數與走勢圖（無評分資料可呈現），改為斷線圖示＋一行文字提示「中斷 N 小時 N 分」
- 全域統計列新增「N 台離線」，與「N 台需注意」並列

#### 影響範圍

- 「正常」區塊標註由「level = 良好或注意（含離線）」修正為「level = 良好或注意・不含離線」
- 全域統計文字新增離線台數
- 此變更為本文件與 IA 4-1 原始敘述（「正常區塊含離線」）的差異，需回頭同步更新 IA 文件或標註為線框圖階段的修正提案

### 11.8 評分詳情頁範例數字校正（勘誤）

#### 問題

先前線框圖範例（走廊 A・鏡頭 3）使用「總分 42、等級危險」作為示意數字，但實際存在兩項錯誤：

1. **總分與五向度分項加總不一致**：範例填入的五向度分數為 18／20／16／3／5，加總為 62，並非卡片標示的 42，兩處數字互相矛盾

## 13. MLOps 面板（IA 6. 對應）

### 13.1 節點分組：7 個子節點收成 4 頁籤

IA 定義 7 個子節點，比照歷史紀錄頁做法，依操作對象分組收成頁籤，避免子節點過多增加認知負荷：

| 頁籤 | 涵蓋節點 | 分組理由 |
|------|---------|---------|
| 每日效能指標 | 6-1 | 獨立，監控性質 |
| Hard Negative Pool | 6-2 | 獨立，資料集管理 |
| 模型版本管理 | 6-3＋6-4＋6-5＋6-6 | 皆圍繞同一份模型版本清單操作（觸發訓練、審核上線、回滾），合併避免同一清單要在四處操作 |
| 固定測試集（唯讀） | 6-7 | 獨立，防止誤解為可隨意更動 |

本輪完成「每日效能指標」頁籤：KPI 卡片（FP/Day、YOLO 信心分數均值、VLM 推翻率）沿用首頁 KPI 卡片樣式；趨勢圖依當日誤報數分級上色（綠／橘／紅），沿用產品既有色彩語言。其餘三頁籤列入待辦。

**參考依據**：`Fulilian_IA資訊架構_v1.md`（第 6 節）、`CareLoop_協作文件_v1_6.md`（GET /mlops/metrics 等 API 定義）。

### 13.2 每日效能指標的攝影機篩選：沿用 8.16 節攝影機選擇器，非 8.24 節區域選擇器

**問題**：MLOps 每日效能指標與環境安全評分歷史都有樓層分組的篩選器，但前者該用「攝影機」層級（8.16 節）還是「區域」層級（8.24 節）？

**判斷依據**：`GET /api/v1/mlops/metrics` 明確定義「可篩選日期範圍、**攝影機**」，且每支攝影機的 YOLO 表現（誤報率、信心分數）取決於個別角度與光線，同區域內不同攝影機表現可能差異很大，若只做到區域層級會混淆診斷訊號（呼應 8.9 節「平均會掩蓋異常」原則）。

**定案**：沿用 8.16 節攝影機選擇器（樓層分組、細到攝影機），不用區域選擇器。KPI 卡片預設顯示全域彙總，選定攝影機後才切換為該攝影機獨立數據。

### 13.3 Hard Negative Pool 頁籤

篩選依誤報類型（坐地／伸展／彎腰／攙扶／其他），沿用 8.21 節已定案的固定清單；攝影機位置格式沿用 8.16 節（樓層・區域・攝影機）；清單含備註、標記者與時間、影片回放入口；頁面頂部提供「匯出全部」對應 `GET /hard-negatives/export`，供 fine-tune 使用。沿用安靜版篩選＋靜態分頁（8.4、8.5 節），性質屬資料集管理，非即時處理。

### 13.4 Hard Negative Pool 誤報類型篩選：改用下拉選單，不用 chip

**問題**：誤報類型清單依 8.21 節機制可能持續新增，原設計用一排 chip 攤開篩選，清單變長會撐大版面、增加認知負荷。

**修正**：改為下拉選單（收合狀態固定寬度，不因分類增加而變化），選項依累積筆數排序，常見分類排前面。

**一般原則（記錄供後續參照）**：篩選項目數量固定不變（如事件影片／環境截圖）用 chip 攤開；數量會持續成長（如誤報類型）用下拉選單，避免版面隨資料成長而跑版。

### 13.6 固定測試集頁籤（6-7，唯讀）

依 SDS 5.9.4：測試集組成（正樣本 120 筆＋Hard Negative 四類共 95 筆）、凍結狀態與建立時間、部署門檻（Recall／誤報率／mAP@0.5）。全頁無任何可編輯欄位或按鈕，強調「凍結」語意（測試集建立後不隨 Hard Negative Pool 更動），避免誤解為可隨意調整，對應 IA 6-7 特別註記事項。

**MLOps 面板 4 個頁籤（每日效能指標／Hard Negative Pool／模型版本管理／固定測試集）全部完成。**

### 13.7 釐清：測試集非訓練回饋迴圈；補上模型版本管理「訓練中」過渡狀態缺口

**釐清**：固定測試集僅作評估把關用，不回饋訓練，流程為單向（觸發→評估一次→人工審核→上線或保留），非自動迴圈（SDS 5.9.4、5.9.5）。

**發現缺口**：13.5 節模型版本管理原設計未呈現「觸發 fine-tune 後、staging 版本產出前」的過渡狀態，訓練屬非同步背景作業（SDS 5.9.5「手動腳本或排程任務」），若頁面無任何回饋，使用者無法確認操作是否生效。

**待補（需後端確認）**：`model_versions.status` 目前 ENUM 僅 staging/production/retired，未定義「訓練中」狀態，需與後端確認是否新增，或改由前端輪詢作業佇列狀態呈現「訓練中」過渡列。

**每日效能指標維持批次更新**（每日／每週統計，SDS 5.9.2），非即時推播，與事件通知的 WebSocket 機制不同，不需比照設計。

### 13.8 補上 Fine-tune 觸發區的 Hard Negative Pool 累積進度提示

### 14.4 警示彈窗三按鈕與誤點防線（修訂第 7 節警示卡按鈕）

按鈕由兩顆改三顆：**確認前往**（主要，`--success` 填色）／**通知人員前往**（次要，端點缺口見待討論 #19）／**誤報**（低視覺權重，`--offline` 外框）。

誤點防線（中控審查第二道防線）兩層設計：
1. **兩段式確認**：接手類操作第一次點擊出現「再按一次送出／取消（誤點）」確認列，第二次點擊才呼叫 API
2. **10 秒復原窗口**：送出後角落顯示「已接手・可復原」提示（`ACK_TOAST_DURATION_MS = 10000`）

**誤報二次確認視窗**（同時解除第 12 章 3-3 子流程待辦）：內嵌事件影片，「確認誤報並關閉」預設反灰、監聽影片 onEnded 播畢才解鎖；誤報類型必選（坐地／伸展／彎腰／攙扶／其他，對應 `hard_negative_pool.label`）、備註選填（`note`）；送出呼叫 `POST /events/{id}/feedback` → SUPPRESSED 後警示才關閉，資料直接餵入 MLOps 資料飛輪。

**逾時參數（程式碼常數現值）**：警示接手期限 90 秒（`CONFIRMED_ALERT_ACK_DEADLINE_MS`）、升級判定 60 秒（`ESCALATION_OVERDUE_MS`）、警示延遲跳出 10 秒（`CONFIRMED_ALERT_DELAY_MS`）；兩段倒數的實際疊加方式依程式邏輯為準。

### 14.5 結案流程與草稿保護（解除待討論 #9）

流程定案：事件發生 → 沒人接手 → 警示收合至儀表板 → 有人接手 → 顯示派人或自己前往 → 回來按「回報完成」→ 彈出結案視窗（**僅接手帳號可填寫**，他人按鈕反灰）→ 填寫處置紀錄 → 確認送出 → RESOLVED，卡片經推播自動移入「今日已結案」（畫面只反映狀態機，不自行搬移卡片）。

- 處置紀錄**本期為純手動輸入**；Agent 交班草稿（IA 3-5）待 Agent 洞察重啟後接上
- **草稿保護**：每 3 秒自動存 localStorage（key：`draft:{eventId}:{userId}`）；警示彈窗蓋上時底層視窗以 CSS 隱藏不 unmount，回來可接續；附手動「儲存草稿」鈕與「已自動儲存 HH:mm」指示；送出成功即清除
- 不做一鍵結案：結案為終態且需留紀錄，必經視窗確認
- 視窗內「已送醫／重大事件」勾選：送出後轉列管（見 14.6），後端未就緒前勾選值隨 payload 送出但不改變前端顯示

### 14.6 列管狀態提案（重大／送醫事件）

參考長照異常事件通報法規（初報／續報／結報三階段）：現場處理完成 ≠ 案件結案。設計為在重大事件路徑插入狀態，不取代既有狀態機：

- 一般事件：已接手 → 回報完成 → 已結案（不變）
- 重大事件：已接手 → 回報完成（勾選已送醫）→ **列管中（REGULATED）** → 續報（原則 5 工作日）／結報（最後續報後原則 10 工作日）→ 已結案

首頁新增「列管追蹤」區塊，置於處理中與已結案之間（有期限壓力但無需立即行動），採藍色系（候選 `--info`）與橘紅「需要行動」區隔。**前置條件**：後端狀態機 ENUM 新增（待討論 #16）、觸發條件待產品定案（待討論 #21）。動工時 CLAUDE.md 必改三處：`EventStatus` 加 `'REGULATED'`、`STATUS_LABEL` 加「列管中」、狀態標籤配色表加一列。
