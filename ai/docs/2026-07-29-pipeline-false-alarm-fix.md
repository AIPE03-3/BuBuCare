## 為什麼要改

### 現況：系統對 9 支正常動作影片全部誤報

用 13 支單一動作短片（走路、撿東西、坐下、跌倒）實測，改動前的正式管線邏輯：

```
pickupobject 5/5 誤報｜sitdown 2/2 誤報｜walk 2/2 誤報
```

其中最誇張的一支 `PickupobjectS9.mp4`（一個人彎腰撿東西），**77 幀被判定為跌倒**。

換成實務語言：**護理師每天會被彎腰、坐下、走路各吵一輪。**
這種系統上線第一週就會被關掉，等於白做。

### 這不是模型爛，是兩條規則太寬

追下去發現誤報集中在兩條規則，跟 pose 模型抓得準不準無關：

| 誤報來源 | 佔比 | 根因 |
|---|---:|---|
| AcT 單獨觸發 | 78.7% | 幾何完全正常（沒躺平、沒遮擋）時，AcT 一句話就能發告警 |
| 遮擋判斷誤觸 | 其餘大部分 | 高度門檻 0.70 把「彎腰」「坐下」一起吃進來 |

## 改了什麼

### 改動 1：AcT 不能單獨觸發（`inference_test.py:749`）

```python
# 改動前 —— 幾何完全正常，AcT 說跌倒就報
elif len(frame_window) == 30 and pred_class == 0 and act_confidence > 0.55:
    should_trigger_fall = True

# 改動後 —— 加一道開關，預設關閉
elif ACT_ALONE_CAN_TRIGGER and len(frame_window) == 30 and pred_class == 0 and act_confidence > 0.55:
    should_trigger_fall = True
```

**白話**：以前 AcT 有「一票決定權」，現在改成「AcT 只能附議，不能提案」。

人真的跌倒時，身體幾乎一定會出現躺平或被家具遮擋的幾何特徵——那兩條防線會先成立，
AcT 在那個分支裡照常參與判斷。被砍掉的只有「幾何完全正常、純粹 AcT 說跌倒」這一種情況，
而實測那正是誤報的最大宗（`WalkS4.mp4` 走路影片就是靠這條報了 54.2% 的幀）。

⚠️ 這條規則被砍掉，等於承認**目前這顆 AcT 權重不夠可靠**。修好它要重訓，見文末。

### 改動 2：遮擋高度門檻 0.70 → 0.50（`inference_test.py:702`）

```python
# 改動前
if (h_box / normal_h_reference) < 0.70 and y2 > (img_h * 0.5): is_occluded_fall = True

# 改動後（常數化）
if (h_box / normal_h_reference) < OCCLUDED_HEIGHT_RATIO and y2 > (img_h * 0.5): is_occluded_fall = True
```

**白話**：這條規則在防「人跌倒後被床/椅子擋住，看不到躺平的姿勢，但人框會變矮」。
問題是**彎腰撿東西、坐下，人框一樣會變矮**。

0.70 這個門檻抓的是「縮到七成以下」——彎腰跟坐下正好落在六~七成，全被誤判。
實測跌倒躺平會縮到**五成以下**，跟前兩者不重疊。

| 動作 | 人框縮到 | 0.70 門檻 | 0.50 門檻 |
|---|---|---|---|
| 彎腰撿東西 | 60~70% | ❌ 誤報 | ✅ 擋掉 |
| 坐下 | 60~70% | ❌ 誤報 | ✅ 擋掉 |
| 跌倒躺平 | < 50% | ✅ 抓到 | ✅ 抓到 |

#### 走過的彎路（避免有人再試一次）

一開始的假設是「撿東西是**短暫**變矮，跌倒是**持續**變矮，加時間門檻就能分」。
寫了 `ai/tune_occlusion.py` 掃描「高度門檻 × 持續幀數」的組合矩陣：

```
高度門檻      1幀      3幀      5幀      8幀     12幀     16幀
0.70      3/4 6/9  3/4 5/9  3/4 5/9  3/4 5/9  3/4 5/9  3/4 5/9
0.60      3/4 5/9  3/4 5/9  3/4 5/9  3/4 5/9  3/4 5/9  3/4 5/9
0.50      3/4 4/9  3/4 4/9  3/4 4/9  3/4 4/9  3/4 4/9  3/4 4/9  ← 採用
0.40      2/4 4/9  2/4 4/9  2/4 4/9  2/4 4/9  2/4 4/9  2/4 4/9  ← 開始漏跌倒
```

**橫向看幾乎沒有變化**——持續幀數從 1 拉到 16，誤報一點都沒少。時間維度的假設是錯的。
**縱向才有變化**——真正的區別是「矮到什麼程度」。

所以最終方案是**一個常數**，不是狀態機。這省下了原本規劃的一整套遮擋狀態機。

## 怎麼回滾

兩個改動都走 `cfg()` 讀 `.env`，不用改程式碼：

```bash
# .env
ACT_ALONE_CAN_TRIGGER=true    # 回到「AcT 可單獨觸發」
OCCLUDED_HEIGHT_RATIO=0.70    # 回到舊的遮擋門檻
```

⚠️ 注意這裡用 `cfg()` 而非 `os.environ.get`：本專案的 `.env` 是用 `dotenv_values`
讀成 dict、**刻意不注入 `os.environ`**，用 `os.environ.get` 會讀不到。

## 評估方法的兩個陷阱（給要看數字的人）

這輪評估被同一個錯誤坑了三次，寫下來避免 review 時重蹈：

### 陷阱 1：「段級召回率」沒有鑑別力

前一輪報過「召回 95%、誤報 56.5%」，看起來是「很準但有點吵」。
補算 baseline 後發現：**每一幀都無腦報跌倒，段級召回率是 100%。**

95% 不是「很準」，是「比亂報還差」。段級召回率只要求「這段時間內報過一次」，
一個持續狂報的系統可以輕鬆拿滿分。評估工具現在強制輸出 baseline 對照。

### 陷阱 2：「有報過就算抓到」會掩蓋漏報

`FallForwardS2` 幀召回 3.8%，用「報過就算」的標準它是成功案例——
而它的存在會讓所有更嚴格的參數組合被判定為「變差」，把正確的方案篩掉。
`tune_occlusion.py` 因此設了 `MIN_FRAME_RECALL = 0.15` 門檻。

**看數字時請以「幀召回率」為準，不要看「抓到幾支」。**

## 沒有解決的問題

| 問題 | 為什麼這次不做 |

| AcT 權重本身不可靠 | 需要重訓，不在這個 PR 範圍 |

### 重訓 AcT 的路徑（下一個 PR）

素材格式已經就緒——`ai/test_demo/` 的短片**檔名即標籤**（`Fall*` / `Walk*` / `SitDown*` …），
`batch_eval.py` 的 `classify_video()` 可直接複用成資料集載入器。
缺的是量：目前每類 2~5 支，訓練需要 20~50 支，並且要補齊往前跌的樣本。

⚠️ 現有的主動學習資料集（`agent/sample_store.py`）**餵不了 AcT**——
那裡存的是單張快照，AcT 吃的是 30 幀序列，形態不同。
