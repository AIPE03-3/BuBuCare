## 2. 系統怎麼運作（只講跟重訓有關的部分）

### 2.1 三層判斷

正式管線是 [ai/inference_test.py](../inference_test.py)。跌倒判斷有三條線：

```
YOLO11s-pose ──> 17 個人體關鍵點
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
   防線 A          防線 B          AcT
   躺平判斷        遮擋判斷      時序分類（← 本次要重訓的）
   （幾何）        （幾何）      （30 幀 = 3 秒）
```

觸發規則（[inference_test.py:754-758](../inference_test.py#L754)）：

```python
if is_physically_lying or is_occluded_fall:          # 幾何先成立
    if window 未滿 or is_ai_thinking_fall or is_occluded_fall:
        should_trigger_fall = True                    # AcT 在這裡「附議」
elif ACT_ALONE_CAN_TRIGGER and ...:                   # ← 預設 False，已被關閉
    should_trigger_fall = True
```

**白話：AcT 現在只能附議，不能提案。** 這是 2026-07-29 為了壓誤報做的降權處置，不是原始設計。

### 2.2 AcT 是什麼

| 項目        | 值                                                                                             | 定義位置                                                                                                       |
| ----------- | ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 架構        | Linear(34→64) → TransformerEncoder(層數 2, d_model 64, nhead 4, ff 128) → Linear(64→32→2) | [inference_test.py:309](../inference_test.py#L309)、[local_pipeline_eval.py:134](../local_pipeline_eval.py#L134) |
| 參數量      | **71,330**                                                                               | —                                                                                                             |
| 輸入        | `[1, 30, 34]` float32                                                                        | [triton_repo/action_transformer/config.pbtxt](../triton_repo/action_transformer/config.pbtxt)                   |
| 輸出        | `[1, 2]` logits，**index 0 = 跌倒、1 = 正常**                                          | 同上                                                                                                           |
| 34 維怎麼來 | `keypoints[:17, :2].flatten()`，即 YOLO 的 17 個關鍵點 (x, y)                                | [local_pipeline_eval.py:395](../local_pipeline_eval.py#L395)                                                    |
| 30 幀是多久 | 素材 20fps、管線跳幀 2 → 有效 10fps →**3 秒**                                          | —                                                                                                             |

⚠ **兩份程式碼各有一份 `ActionTransformer` 定義（`inference_test.py` 與 `local_pipeline_eval.py`），必須完全一致**，否則 `state_dict` 載不進去。改架構要兩邊一起改。

### 2.3 部署路徑

```
訓練產出 .pth ──> 轉 ONNX ──> ai/triton_repo/action_transformer/<版本>/model.onnx ──> Triton serving
                                                                                          │
                                            inference_test.py 透過 triton_act_client.py ◄──┘
```

`ai/action_transformer.pth` 本身**不參與正式推論**，只給本機評估工具 [local_pipeline_eval.py](../local_pipeline_eval.py) 直接載入用。

## 3. 現況：問題在哪

### 3.1 目前的數字（13 支單一動作短片實測）

| 指標                                          |                           值 |
| --------------------------------------------- | ---------------------------: |
| 正常動作幀誤報率                              |                         2.0% |
| 跌倒幀召回率                                  |                        41.5% |
| 被誤報過的正常影片                            |                       4/9 支 |
| **前跌（`FallForwardS2.mp4`）召回率** | **0.0%** ← 完全抓不到 |

複現指令：

```bash
ai/.venv/bin/python ai/batch_eval.py --modes geo-first --occ-height 0.50
```

### 3.2 兩個沒解決的問題

**問題一：AcT 不可靠，只好把它降權。**
上一輪發現，「幾何完全正常但 AcT 說跌倒」這條路徑貢獻了 **78.7% 的誤報**。走路影片 `WalkS4.mp4` 光靠這條就誤報了 54.2% 的幀。處置方式是關掉它（`ACT_ALONE_CAN_TRIGGER=false`），代價是 AcT 從三條防線之一降級成配角。

**問題二：俯視鏡頭看不到往前跌。**
兩條幾何防線（躺平角度、人框變矮）在俯視視角下對「往前跌」幾乎無感——人往前趴倒時，從天花板往下看，軀幹的**投影**角度變化極小。這是幾何方法的先天盲區，調參數解決不了。

**這兩個問題只有一個共同解法：讓 AcT 真的變準。**

### 3.3 我懷疑的根因（**假設，尚未驗證**）

[local_pipeline_eval.py:382](../local_pipeline_eval.py#L382) 用的是 `result.keypoints.xyn`——**對整張影像歸一化**的座標，不是對人框歸一化。

這代表模型看到的是「這個人在畫面的哪個位置、佔畫面多大」，而不是「這個人的身體是什麼形狀」。推論：人走到畫面另一側、或站得離鏡頭遠一點，特徵分布整個平移，模型就失效。

**但這只是假設，沒有實證。** 因此本計畫刻意把它排在「先用原特徵重訓拿 baseline，再 A/B 驗證」，而不是一開始就改。改特徵會同時動到三處程式碼加 Triton 設定，是最貴的改動，要用數字決定值不值得。

### 3.4 評估方法的三個陷阱（前人踩過，不要再踩）

| 陷阱                                       | 說明                                                                                                                               |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| **不要看「段級召回率」**             | 「這段時間內報過一次就算抓到」——一個每幀都無腦報跌倒的系統可以拿 100 分。前一輪的「召回 95%」就是這樣來的假數字                  |
| **不要看「抓到幾支影片」**           | `FallForwardS2` 幀召回 3.8%（123 幀裡報 4 幀）用這標準算「成功」，但實際上訊號送出去時人早就躺很久了。這個標準會把正確的方案篩掉 |
| **一律看「幀召回率」與「幀誤報率」** | [batch_eval.py](../batch_eval.py) 已強制輸出 baseline 對照，照它的輸出看                                                            |

另外：`ai/test_demo/test1.mp4`~`test3.mp4` 是舊的**剪接長片**（一支裡混了多段跌倒與正常），[batch_eval.py:51](../batch_eval.py#L51) 用 `SKIP_PREFIXES = ("test",)` 明確跳過它們。不要拿來評估。

## 5. 資料規劃（唯一的硬瓶頸）

### 5.1 CAUCAFall：能用，但不夠，而且視角不對

現有的 13 支短片來自 **CAUCAFall**（Universidad del Cauca / Universidad de la Amazonia），已確認。

| 項目        | 內容                                                                          |
| ----------- | ----------------------------------------------------------------------------- |
| 取得處      | [Mendeley Data — CAUCAFall](https://data.mendeley.com/datasets/7w7fccy7ky/4)  |
| 規模        | **10 位受試者 × 10 種動作 = 100 支影片**                               |
| 跌倒類（5） | 前跌、後跌、左側跌、右側跌、從坐姿跌落                                        |
| 日常類（5） | 走路、跳躍、撿東西、坐下、跪下                                                |
| 格式        | `.avi` 影片 + `.png` 逐幀圖 + `.txt` 逐幀人體框標註                     |
| 場景        | 居家環境 RGB 相機，含遮擋、光線變化（自然光/人工光/夜間）、不同衣著與地板材質 |

**三個限制，直接決定了整個資料策略：**

1. **總量只有 100 支。** 全部拿來，滑動視窗（stride 5）大約只能產出 1,500 個訓練樣本。對 7 萬參數的模型偏少，且同一受試者的樣本高度相關。
2. **視角是側面居家鏡頭，我們的正式環境是俯視固定鏡頭。** 這是最大的 domain gap。**直接拿 CAUCAFall 訓出來的模型，在俯視鏡頭上不會work。**
3. **沒有「主動躺下」這個類別。** 這是最關鍵的負樣本——人自己躺到床上，幾何上跟跌倒完全一樣（躺平、人框變矮），唯一能區分的是**速度**。缺這類負樣本，模型永遠學不會這個區別。

### 5.2 結論：CAUCAFall 當 pre-train，自錄俯視資料是必要項

```
CAUCAFall 100 支（側面）  ──> 預訓練，讓模型先學會「跌倒的動作長什麼樣」
                              │
自錄 100+ 支（俯視）      ──> 微調 + 測試，讓模型適應真實視角
```

**自錄不是加分項，是必要項。** 沒有俯視資料，做出來的數字無法反映上線後的表現。

### 5.3 自錄規格

**器材與機位（最重要，錄錯就全廢）**

| 光線            | 至少錄三種：日光、室內燈、夜間微光。各佔約 1/3                            |

| ---------------------- | -------------- | ------------: | ---------------------------------------------------- |

> 訓練集**不需要**照真實世界的跌倒發生率配比。照真實比例（跌倒佔 0.01%）模型會學會「永遠說正常」然後拿 99.99% 準確率。

**安全要求（不可省略）**

- 地面鋪**厚墊**，跌倒動作全部落在墊上
- 由**年輕健康的組員**演示，禁止找長者或行動不便者實錄
- 每次跌倒動作前後留 3 秒以上的正常動作（模型需要看到「跌倒前」的狀態）

**錄製成本估算**

6 位組員 × 10 種動作 × 平均 2.5 次 = 150 支。每支約 10 秒，含重設與換場約 1 分鐘 → **每人 25~30 分鐘，一個下午錄得完。**

**倫理**：受試者為組員本人，需簽署影像使用同意書（載明用途、保存期限、是否對外發布）。若場地為實際醫療機構，須先確認該機構的規範。

### 5.4 標註：只需要標「跌落起訖」

**這是唯一需要人工的環節，也是最容易做錯的地方。**

❌ **錯誤做法**：沿用現有的「檔名即標籤」，把整支跌倒影片的所有幀都標成跌倒。
→ 一支跌倒影片裡，前 3 秒站著、中間 1 秒跌落、後面 5 秒躺著。全標成「跌倒」，模型會學成「**躺著 = 跌倒**」——那正是現在誤報的來源。

✅ **正確做法**：標出每支跌倒影片的**跌落動作起訖時間**（從失去平衡到身體完全著地為止，不含之後躺著的部分）。

**標註格式已經有現成的 parser，直接複用，不要另外做工具。**
[local_pipeline_eval.py:170](../local_pipeline_eval.py#L170) 的 `parse_label_file()` 支援兩種寫法，`#` 開頭是註解：

```
# FallForward_S03.mp4
0:03-0:05
```

或

```
frame 62-98
```

| 項目         | 估計                                                                            |
| ------------ | ------------------------------------------------------------------------------- |
| 需標註的影片 | 只有跌倒類（CAUCAFall 50 支 + 自錄 72 支 = 122 支）。正常類全片皆負樣本，不用標 |
| 每支耗時     | 1~2 分鐘                                                                        |
| 總計         | **3~4 小時**，可分給 2 人                                                 |
| 品質控管     | 兩人各標同樣 20 支，比對差異。起訖幀差 > 5 幀就先對齊標準再全面開標             |

### 5.5 視窗標籤規則

⚠ **這節容易寫錯，錯了會直接產出 0 個正樣本。先看清楚兩者的長度差：**

| | 有效幀（跳幀 2 後） | 秒數 |
|---|---:|---:|
| AcT 視窗 | 30 | 3.0 |
| 一次跌落動作 | 約 10~15 | 1.0~1.5 |

**視窗遠比跌落動作長。** 所以判準不能是「視窗有多少比例是跌倒」——那個比例最高也只有 50% 左右，設 50% 門檻等於一個正樣本都拿不到。

判準要反過來，問「**這個視窗有沒有看完整場跌倒**」：

| 條件 | 標籤 |
|---|---|
| 視窗 ∩ 跌落區間 ≥ **跌落區間長度 × 80%** | **正樣本（跌倒，class 0）** |
| 視窗 ∩ 跌落區間 = 0 | **負樣本（正常，class 1）** |
| 其餘（只看到一半跌倒） | **直接丟棄** |

這才對應 AcT 在管線裡實際要回答的問題：「最近 3 秒內發生過跌倒嗎」。

中間地帶丟掉是刻意的——「跌到一半」的視窗標成什麼都不對，留著只會製造標籤噪聲。

> **實作提醒**：標註完成後，先跑一次跌落時長的統計分布再定 stride。
> 若實測跌落動作明顯短於 10 幀或長於 20 幀，80% 這個係數要跟著調。
> 不要照抄，要用你自己資料的數字。

### 5.6 資料切分（最容易自欺的一步，而且有一個陷阱）

**必須按「受試者」切，不可按影片隨機切。**

同一個人的不同影片有高度相關的體型與動作習慣。隨機切會讓驗證準確率飆到 95%，上線後打回原形。**這是這類專案最常見的造假方式，通常還是無意的。**

#### ⚠ 陷阱：`ai/test_demo/` 的 13 支就是 CAUCAFall 的子集

下載完整的 100 支 CAUCAFall 拿去訓練，**這 13 支必然被包含進去**——你唯一的基準測試集當場被污染，所有既往數字（誤報 2.0% / 召回 41.5%）失去對照意義，而且**無法復原**。

檔名裡的 `S<數字>` 就是 CAUCAFall 的 subject 編號。13 支的分布：

| subject | test_demo 裡的影片 |
|---|---|
| S1 | PickupobjectS1 |
| **S2** | **FallForwardS2**、SitDownS2 |
| S3 | PickupobjectS3 |
| S4 | WalkS4 |
| **S5** | **FallLeftS5**、**FallRightS5**、PickupobjectS5 |
| S6 | PickupobjectS6 |
| S8 | SitDownS8 |
| S9 | PickupobjectS9 |
| **S10** | **FallBackwardsS10**、WalkS10 |

**4 支跌倒基準影片剛好只落在 S2、S5、S10 三個 subject。** 利用這點，指定切分：

```
CAUCAFall:  train = S1, S3, S4, S6, S7  (50 支)
            val   = S8, S9              (20 支)
            test  = S2, S5, S10         (30 支) ← 基準影片全在這裡

自錄:       train = 組員 A~D | val = 組員 E | test = 組員 F
```

**保住的基準影片（7 支，7 種動作全覆蓋）：**

| 影片 | 動作 | 為什麼重要 |
|---|---|---|
| FallForwardS2 | 前跌 | **本次重訓的核心指標，唯一的前跌樣本** |
| FallBackwardsS10 | 後跌 | |
| FallLeftS5 / FallRightS5 | 左跌 / 右跌 | 目前唯二抓得到的跌倒類型 |
| SitDownS2 | 坐下 | 誤報基準 |
| PickupobjectS5 | 撿東西 | 誤報基準 |
| WalkS10 | 走路 | 誤報基準 |

**犧牲的（6 支，全是正常動作）**：PickupobjectS1 / S3 / S6 / S9、SitDownS8、WalkS4。
誤報基準從 9 支縮到 3 支。

這個取捨是刻意的：**跌倒召回率的基準完整保留，誤報基準縮水**。理由是誤報基準之後會被自錄的俯視資料大量補回來，而前跌基準補不回來——那是唯一一支。

> ⚠ **開工前必須核對**：上表的 subject 對應是從檔名推斷的。下載 CAUCAFall 後，
> 先確認 `FallForwardS2.mp4` 確實來自 Subject 2 的資料夾。**對應錯了整個切分失效。**

#### 鐵則

**現有的 13 支 `ai/test_demo/` 短片，凡是落在 test 的都不准進訓練集。** 若因故必須調整切分，優先保住 `FallForwardS2`。

### 5.7 只用 CAUCAFall 這 100 支，先訓一次（強烈建議，且不必等自錄）

**可以先訓，而且應該先訓。** 但要清楚它能回答什麼、不能回答什麼，否則會拿一個不可信的數字去做決策。

#### 樣本數估算

⚠ 依 5.6 的切分，**訓練集只有 50 支**（S1/S3/S4/S6/S7），不是全部 100 支。下表算的是訓練集，stride = 1：

| | 計算 | 數量 |
|---|---|---:|
| 跌倒影片 | 25 支 × 每支約 20 個合格視窗 | **~500 正樣本** |
| 日常影片 | 25 支 × 每支約 65 個視窗 | **~1,600 負樣本** |
| 跌倒影片的非跌落片段 | 站立、躺著的部分 | **~1,000 負樣本** |
| | 正:負 | **約 1 : 5** |

看起來有 500 個正樣本，**但這是滑動視窗製造的假象**。

> **真正的獨立資訊量只有 25 次跌倒事件**（5 位受試者 × 5 種跌法）。
> 同一次跌倒切出來的 20 個視窗彼此高度相關，對模型而言接近同一個樣本。
> 對 7 萬參數的模型來說，25 個獨立正樣本**非常少，過擬合幾乎必然發生**。
>
> 這正是把 1A 定位成「可行性驗證」而非「驗收」的原因之一——
> 除了視角不對，樣本量本身也撐不起一個可信的結論。
> **不要因為 1A 的數字不好看就放棄整個計畫**，1A 只有一票否決權中的一半：
> 唯有「連加上加速度特徵都救不回前跌」才構成退場理由（見階段 1A 的決策表）。

類別不平衡用 class weight 或加權損失處理即可，不需要對資料做上/下採樣。

#### 這個先導實驗能回答什麼

| 能回答 | 不能回答 |
|---|---|
| 整條管線（抽特徵→訓練→匯出→評估）通不通 | 模型在**俯視鏡頭**上表現如何 |
| 「換資料 + 正確的幀級標註」能否改善 AcT 在**同分布**上的表現 | 是否可以把 `ACT_ALONE_CAN_TRIGGER` 打開 |
| 34 維絕對座標特徵**有沒有救**（第 3.3 節的假設） | 是否可以上線 |
| 前跌在**側面視角**下抓不抓得到 | 前跌在**俯視視角**下抓不抓得到 |
| 自錄到底該錄多少支才夠 | — |

#### 為什麼值得先做

1. **成本極低**：不用等場地、不用等同意書、不用等器材。下載 + 標註 50 支 + 訓練 ≈ **2~3 天**。
2. **資訊價值高**：結果會直接決定自錄的規模。若側面視角下前跌召回率就衝到 60%，代表方法可行、自錄 150 支是對的；若連側面都抓不到，**那自錄 150 支也救不了**，該轉去評估感測器方案（見第 4 章退場條件），可以省下 2 週。
3. **把管線的坑先踩完**：train/serve 特徵不一致、ONNX 匯出格式、Triton 載入——這些跟資料無關的問題，用 100 支就能全部踩完，等自錄資料到位時可以直接開訓。

#### ⚠ 唯一的禁止事項

**不准拿 CAUCAFall 訓出來的模型上線，也不准用它的數字決定是否上線。**
側面居家鏡頭與俯視固定鏡頭的 domain gap 沒有被驗證過，這個數字在正式環境不成立。
它只是可行性驗證（feasibility check），不是驗收。

## 7. 執行階段

每個階段都有可驗收的產出，做不出來就停下來討論，不要硬闖下一階段。

### 階段 0：把管線接通（0.5~1 天）

**目的不是訓出好模型，是證明「抽特徵 → 訓練 → 匯出 → 評估」這條路是通的。**
用現有 13 支素材跑，必定過擬合，**那沒關係**。此階段唯一的驗收標準是「跑得完、數字出得來、ONNX 能被 Triton 載入」。

需新增 3 支腳本（放 `ai/train/`）：

| 檔案                             | 輸入 → 輸出                                   | 關鍵約束                                                                                                                                                                                                   |
| -------------------------------- | ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ai/train/extract_features.py` | 影片目錄 + 標註檔 →`features.npz`           | ⚠**必須 `from local_pipeline_eval import extract_pose_state` 複用既有函式，嚴禁自己重寫一份特徵抽取。** train 與 serve 的特徵不一致是這類專案最常見的死法，而且極難 debug                         |
| `ai/train/train_act.py`        | `features.npz` → `action_transformer.pth` | 架構必須與[inference_test.py:309](../inference_test.py#L309) **逐字一致**（含 `batch_first=True`），否則權重載不進正式管線                                                                          |
| `ai/train/export_onnx.py`      | `.pth` → `model.onnx`                     | 輸出必須符合[config.pbtxt](../triton_repo/action_transformer/config.pbtxt)：input name `input` dims `[1,30,34]`、output name `output` dims `[1,2]`、FP32。**這支現在完全不存在（見第 1 章）** |

**階段 0 的驗收**：

```bash
# 抽特徵 → 訓練 → 匯出 → 用 batch_eval 出數字，四步不報錯
ai/.venv/bin/python ai/batch_eval.py --modes geo-first --occ-height 0.50
```

### 階段 1A 與 1B：兩條線並行跑，不要串行等待

**這兩條線沒有相依關係，同時開始。** 1A 的結果會回頭修正 1B 的規模。

#### 階段 1A：CAUCAFall 先導實驗（2~3 天，**現在就能開始**）

不需要場地、器材、同意書。詳細定位見第 5.7 節。

| 工作 | 負責 | 耗時 |
|---|---|---|
| 下載 CAUCAFall、確認授權條款是否允許本專案用途 | 1 人 | 0.5 天 |
| 幀級標註 50 支跌倒影片（跌落起訖） | 1~2 人 | 1.5~2 小時 |
| 統計跌落時長分布，回頭校正 5.5 的 80% 係數與 stride | 1 人 | 0.5 小時 |
| 按受試者切分（train S1~S6 / val S7~S8 / test S9~S10） | 1 人 | 0.5 天 |
| 訓練 + 評估 | 1 人 | 0.5 天 |

**1A 的產出是一個決策，不是一個模型：**

| 1A 的結果 | 代表什麼 | 下一步 |
|---|---|---|
| 前跌召回率 > 50%（側面視角） | 方法可行，瓶頸單純是資料量與視角 | 1B 照原規模錄 150 支 |
| 前跌召回率 20~50% | 可行但吃緊 | 1B 把前跌樣本再加倍（24 → 40 支） |
| **前跌召回率 < 10%** | **34 維座標序列本質上表達不了前跌** | **先做階段 3 的實驗 B（加速度特徵）再決定要不要錄**。若仍無效，觸發第 4 章退場條件，改評估感測器方案，**省下 2 週** |

⚠ **1A 的模型不准上線，1A 的數字不准用來做上線決策。** 理由見 5.7 節末。

#### 階段 1B：自錄俯視資料（1~2 週，與 1A 並行）

| 工作 | 負責 | 耗時 |
|---|---|---|
| **現場量測正式部署的鏡頭型號、高度、角度並拍照存證** | 1 人 | 0.5 天 |
| 場地協調、同意書、鋪墊等前置 | 1 人 | 1 天 |
| 自錄 150 支 | 6 人 | 1 個下午 |
| 幀級標註 72 支跌倒影片 | 2 人 | 2~3 小時 |
| 按受試者切分並寫資料集 README | 1 人 | 0.5 天 |

⚠ 開錄前**務必**先完成鏡頭量測。機位不對，150 支全部白錄，而且這是本計畫唯一不可挽回的錯誤。

### 階段 2：Baseline 重訓（1 天）

**不改架構、不改特徵，只換資料。** 這是誠實的對照組。

| 實驗 | 訓練資料 | 目的 | 何時能跑 |
|---|---|---|---|
| **B1** | 只用 CAUCAFall | 看公開資料集單獨能到哪 | **階段 1A 結束就能跑** |
| B2 | 只用自錄俯視 | 看自錄資料單獨能到哪 | 需等 1B |
| B3 | CAUCAFall 預訓練 → 自錄微調 | 預期最好 | 需等 1B |

B1 其實就是階段 1A 的產物，這裡列出是為了與 B2/B3 對照。

**驗收只看 B2 與 B3。** 若 B3 就達到第 4 章的及格線，階段 3 全部不用做，直接跳階段 4。

> 若 B3 沒有優於 B2，代表 CAUCAFall 預訓練幫不上忙（domain gap 太大）。
> 這是正常結果，不必勉強——直接採用 B2，並把自錄量再加 50 支。

### 階段 3：架構 A/B（1~2 天，僅在階段 2 未達標時執行）

**按成本由低到高做，達標就停。**

| 順序 | 實驗                      | 改動                                                                                      | 風險 | 要改幾處                                                     |
| ---- | ------------------------- | ----------------------------------------------------------------------------------------- | ---- | ------------------------------------------------------------ |
| 1    | **C. 加權損失**     | 對前跌樣本與 hard negative 加權；試 focal loss                                            | 低   | 只改訓練腳本，推論端完全不動                                 |
| 2    | **A. 人框歸一化**   | 座標改成對人 bbox 歸一化，而非對整張影像                                                  | 中   | `inference_test.py`、`local_pipeline_eval.py`、重出 ONNX |
| 3    | **B. 加入速度特徵** | 34 維 → 68 維（座標 + 幀間差分）。**這是區分「主動躺下」與「跌倒」的唯一物理依據** | 高   | 上述三處 +`config.pbtxt` 的 input dims + Triton 重載       |

實驗 A 是用來驗證第 3.3 節那個假設的。如果 A 沒有帶來改善，那個假設就是錯的，寫進文件別讓下一個人再試一次。

### 階段 4：評估與門檻回校（0.5~1 天）

1. 全套跑 `batch_eval.py`，對照第 4 章的驗收標準
2. **把 `ACT_ALONE_CAN_TRIGGER=true` 打開重測**——這是本次重訓成敗的關鍵指標
3. 重跑 [tune_occlusion.py](../tune_occlusion.py)：AcT 變強後，`OCCLUDED_HEIGHT_RATIO` 這個 0.50 的門檻可能可以放寬回 0.60~0.70，把召回率賺回來。**這個掃描很便宜，一定要做**
4. 產出一份對照文件放 `ai/docs/`，格式參考 [2026-07-29-pipeline-false-alarm-fix.md](2026-07-29-pipeline-false-alarm-fix.md)

### 階段 5：上線（0.5 天）

```bash
# 1. 新權重轉 ONNX，放到「新的版本目錄」，不要覆蓋 1/
ai/.venv/bin/python ai/train/export_onnx.py \
    --weights ai/action_transformer_v2.pth \
    --out ai/triton_repo/action_transformer/2/model.onnx

# 2. 確認檔案存在後，才改 config.pbtxt 指向 v2
```

在 [action_transformer/config.pbtxt](../triton_repo/action_transformer/config.pbtxt) 加：

```
version_policy: { specific { versions: [ 2 ] } }
```

⚠ **不要靠「Triton 會自動載最大版本號」隱式切版。** 這個坑 `rt_detr` 已經踩過一次：v3 目錄只有 `.onnx` 沒有 `.plan`，Triton 預設載最大版本 → 整台 server 起不來，連本來正常的另外兩顆模型也一起無法服務。詳見 [triton_repo/README.md](../triton_repo/README.md) 的事故記錄。

**回滾**：把 `version_policy` 改回 `versions: [ 1 ]`，重啟 Triton。舊版 v1 目錄不要刪。

## 8. 時程與風險

### 8.1 總時程

階段 1A 與 1B 並行，所以日曆時間不是各階段相加。

| 階段 | 純工時 | 日曆時間 | 相依 |
|---|---:|---|---|

| 1B 自錄（卡在場地協調） | 3 人日 | **1~2 週** | 與 1A 並行 |
| 2 baseline 重訓 | 1 人日 | 1 天 | 需 1B |
| 3 架構 A/B（可能不需要） | 2 人日 | 1~2 天 | — |
| 4 評估與回校 | 1 人日 | 1 天 | — |
| 5 上線 | 0.5 人日 | 0.5 天 | — |
| **合計** | **9~13 人日** | **3~4 週** | |

**第一週就會有數字**（階段 0 + 1A）。3~4 週那個數字是卡在自錄的場地協調，不是卡在技術。

若 1A 的結果觸發退場條件（前跌召回 < 10% 且加速度特徵也無效），**整個計畫在第一週結束，省下後面 3 週**。這正是先做 1A 的價值。

### 8.2 風險

| 風險                                        | 徵兆                             | 應對                                                                                               |
| ------------------------------------------- | -------------------------------- | -------------------------------------------------------------------------------------------------- |
| **拿 CAUCAFall 的數字當驗收** | 1A 數字漂亮，有人提議直接上線 | **禁止**。側面視角的數字在俯視環境不成立，見 5.7 節末。驗收只認 B2/B3 |
| **視窗標籤規則寫錯** | 訓練集裡正樣本數為 0 或個位數 | 見 5.5 節。判準是「視窗有沒有涵蓋整場跌倒」，不是「視窗有幾成是跌倒」 |
| 自錄機位與正式部署不一致                    | 錄完才發現角度不對               | **階段 1B 開錄前先量測並拍照存證**。這是唯一不可挽回的錯誤                                    |
| CAUCAFall 預訓練幫不上忙（domain gap 太大） | 階段 2 的 B3 沒有優於 B2         | 正常結果，不必勉強。直接只用自錄資料，並把自錄量再加 50 支                                         |
| 訓練與推論特徵不一致                        | 離線評估很漂亮、上 Triton 後變差 | 階段 0 就建立比對：同一支影片，比較`local_pipeline_eval.py` 與 Triton 的 AcT 輸出，差異須 < 1e-4 |
| 標註品質不一致                              | 兩人標的起訖幀差很多             | 先標 20 支重疊樣本對齊標準，再全面開標                                                             |
| 誤報下降但召回也下降                        | 階段 4 數字                      | 依第 4 章退場條件，**不上線，維持現狀**                                                      |
| 前跌怎麼樣都抓不到                          | 所有實驗前跌召回 < 10%           | 停止調 AcT。這是感測器問題，需評估深度攝影機或多機位，另開議題                                     |

## 9. 不可違反的鐵則（給接手的人與他的 agent）

1. **特徵抽取只能有一份實作。** 訓練端必須 import [local_pipeline_eval.py](../local_pipeline_eval.py) 的 `extract_pose_state()`，不准複製貼上或重寫。
2. **`ActionTransformer` 的架構定義有兩份**（`inference_test.py` 與 `local_pipeline_eval.py`），**改一份就要改另一份**，且要與 ONNX、`config.pbtxt` 同步。
3. **`ai/test_demo/` 的 13 支短片是 CAUCAFall 的子集**，訓練前必須依 5.6 的切分把它們所在的 subject（S2/S5/S10）整組劃進測試集。**污染了無法復原。** 若被迫調整切分，優先保住 `FallForwardS2`。
4. **資料按受試者切分，不准按影片隨機切。**
5. **永遠不覆蓋 `ai/action_transformer.pth` 與 `triton_repo/action_transformer/1/`。** `*.pth` 和 `*.onnx` 都不進版控，覆蓋即永久遺失，回滾路徑一併消失。動手前先備份（見第 1 章）。
6. **評估只看幀召回率與幀誤報率**，不看段級召回率、不看「抓到幾支影片」。
7. **只用 CAUCAFall 訓出來的模型不准上線**，它的數字也不准用來做上線決策。那是側面視角，正式環境是俯視，它只是可行性驗證。
8. **視窗標籤的判準是「視窗有沒有涵蓋整場跌倒」**，不是「視窗有幾成是跌倒」。視窗（3 秒）比跌落動作（1~1.5 秒）長得多，用後者會產出 0 個正樣本。見 5.5 節。
9. **Triton 上新版本一律用新的版本目錄 + 明確的 `version_policy`**，不要覆蓋 `1/`、不要靠自動選版。
10. **改 `.env` 相關設定時要用 `cfg()` 讀取，不是 `os.environ.get`。** 本專案的 `.env` 是用 `dotenv_values` 讀成 dict、**刻意不注入 `os.environ`**，用 `os.environ.get` 會讀不到（這個坑實際踩過）。
11. **達不到驗收標準就不上線。** 現況 2.0% 誤報是可用的，維持現狀永遠優於讓系統變差。
